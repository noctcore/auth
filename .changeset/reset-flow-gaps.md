Four changes to password reset, for apps that run the whole reset flow on the package.

**Fix: no reset link outlives a failed password write.** `resetPassword` and `changePassword` used to write the new hash first and void the reset links, codes and tickets after it, so a crash or a store error right after the write left a code-mode ticket, or a link requested meanwhile, that could still set the password. They now void every reset token (and an email change started under the old password) before the write, and once more after it. A failed write leaves the old password and no link: the user asks again. Once the hash is written, a failure to lift the lockout or to mark the address verified is logged as `Step after a password write failed` (with the step and the user id) and the reset answers ok instead of throwing; the lock stays until it ends or an admin clears it. A failure to end the sessions still throws.

**New: `auth.inspectPasswordReset({ token, meta })`** checks a reset link (the ticket in code mode) without spending it and without mailing anything, for a reset page on load. A live link answers `ok({ user, expiresAt, secondFactorRequired })`; an unknown, expired or spent one answers `invalid_token`, whichever it is. It counts on the `password-reset` door with `resetPassword`, and writes `password.reset_inspected` or `password.reset_inspect_failed` (no user id for an unknown token). `secondFactorRequired` comes from the new `passwordResetRequirements` hook (`({ user }) => ({ secondFactor?: boolean })`, any `true` wins), which the two-factor plugin answers for a confirmed factor; an app that demands its own factor in `beforePasswordReset` answers it there. The hook may also return a `refuse(...)`, which the check answers, so an account your app always refuses at reset looks the same on the page; an account in an email revert lockout answers `invalid_token`, as its reset does. `TokenRedemption` gains `expiresAt` on a valid redemption. `@noctcore/auth-trpc` adds `inspectPasswordResetInput` and `resetInspectionOutput`.

**New audit event `password.reset_issued`** (`userId`, `data.kind` `link` or `code`, the request's IP and user agent) when a reset job stores a link or code, before its mail is handed over, also when the job runs on your queue. Nothing is written for a request that sends nothing; those keep writing `password.reset_request_ignored`.

**New: account mails say where the request came from.** Mail events sent by a request on the owner's account (`password-reset`, `password-reset-code`, `password-changed`, `lockout`, `verify-email`, `account-exists`, `email-change-confirm`, `email-changed`, `email-change-reverted` and the two-factor plugin's mails) carry an optional `meta: { ip, userAgent? }` (type `MailRequestMeta`). `PasswordResetJob` gains an optional `userAgent`, captured at the request, so the reset mail and the job's audit rows carry the request's IP and user agent when the job runs on a queue worker. `email-change-in-use` and `invitation` never carry it, since they go to someone other than the account the request acted on. A mailer that ignores `meta` keeps working; if your queue stores the whole event, it now stores the IP and user agent too. Jobs queued before this release have no `userAgent` and run as before.
