Every session check (`authed`, `freshAuth`, `role`, `protectedProcedure`, and the nestjs-trpc `AuthGuardMiddleware`, `AuthedMiddleware`, `FreshAuthMiddleware` and `RoleMiddleware`) now keeps a subscription's events behind it. tRPC builds the context once per HTTP request and an SSE subscription (`httpSubscriptionLink`) is one request that stays open, so a stream opened before a sign-out, a password change or a revocation kept sending events to that browser until the client left or `sse.maxDurationMs` ended it. Now, before an event leaves, when the last check that saw the session live started longer ago than the new `revalidateSubscriptions` option of `createAuthContext` (default `'30s'`, a number in seconds, `0` for every event, `false` to turn it off), the session is validated again without counting as activity and its user loaded, and a refusal ends the stream with `session_expired` (or `two_factor_enrollment_required`) in place of the event. A stream that sends nothing reads nothing. A store failure ends the stream with `internal`, which the client retries by reconnecting. The bound is read on the core's clock, which is not monotonic: a backwards step delays the next check. A procedure that returns an observable is read as an async iterable, as tRPC's SSE handler reads it.

Behaviour change: an open subscription behind a session check used to keep sending events after its session was revoked, expired or its user deleted; it now ends with `session_expired` at the first event after the bound. The check does not count as activity, on purpose: a page that only reads an SSE stream sends no activity, so the stream ends with `session_expired` once `idleTimeout` passes and the user is signed out. A bad `revalidateSubscriptions` value stops the boot with an `AuthConfigError`. Pass `revalidateSubscriptions: false` to keep the old behaviour.
