## What goes wrong

Browsers attach cookies to every request for a site, including requests another site triggers: a hidden form that posts to your `/logout` or `/change-email`, or a link to a URL that changes state. The browser's same-origin policy stops the other site from reading the response, but some requests (a `GET`, a form `POST`) are sent anyway.

## The rule

**Never change state on `GET`.** A redirect or an image tag can trigger a `GET` from anywhere. Every flow that changes something is meant for `POST` or another unsafe method. Then three layers, each stopping what the one before can miss.

### The cookie: `SameSite=Lax`

The browser leaves the session cookie off cross-site subrequests and cross-site form posts, while still sending it when a user follows a link to your site. This is the default and stops most attacks on its own, but not all:

- sibling subdomains count as the same site;
- very old browsers ignore the attribute.

### Where the request came from

- **One origin.** `verifyFetchSite` refuses any unsafe request whose `Sec-Fetch-Site` header is missing or not `same-origin`. Browsers set that header themselves and page scripts cannot change it.
- **A desktop shell or trusted sibling subdomains.** Apps that also serve a desktop shell (an `app://` origin) or trusted sibling subdomains use `verifyRequestOrigin` with an explicit allowlist instead, refusing requests without an `Origin`.

### Cross-site origins you name

A shell's requests say `Sec-Fetch-Site: cross-site`, like an attack's. The NestJS and tRPC adapters accept them only from origins listed in `csrf.crossSiteOrigins` (empty by default), matched exactly with no wildcards; the core's `verifyFetchSite` takes the same list with the request's `origin`.

<Aside type="caution" title="A listed origin is trusted as much as your own">
  A page that can run script there can send requests the fetch-metadata check no longer stops, and
  only the double-submit token, which stays on, still stands in its way. List a custom scheme only
  the shell serves, never a web origin you do not control, and give the cookies the shell needs
  `SameSite=None` through `session.cookie.sameSite` (see [Cookies and desktop
  shells](/auth/learn/cookies-and-desktop-shells/)); the adapters' CSRF cookies follow it.
</Aside>

### A signed double-submit token

`createCsrfToken` mints a random nonce with an HMAC over it and a binding, which the page reads from a cookie and echoes in a header. `verifyCsrfToken` checks that:

- the cookie and the header match;
- the nonce is 32 hex characters;
- the HMAC is valid for the current binding.

The MAC input is length-prefixed (`csrf:<binding length>:<binding>:<nonce>`), so no binding and nonce pair can be read as another. The HMAC stops a sibling origin that can write cookies from planting a pair of its own; the binding stops a token minted for one session from working in another.

The secret must be at least 32 bytes, should be used for CSRF only (not the auth secret), and can be rotated with a list of accepted previous secrets. During a rotation, hand out a token under the current secret whenever a safe request arrives with one signed by a previous secret, or no client ever moves and the previous secret can never be removed without refusing each of them once. Keep the strict compare of header and cookie while doing it: a page that kept the old token in memory is refused once after another request replaced the cookie, and must read the token again (or retry once after a safe request). Accepting an old-secret header over the new cookie would let anyone holding the previous secret, and the binding, mint a header.

### A binding before sign-in too

Signed in, bind to the session. Signed out, do not bind every visitor to one shared value, or a token pair minted in the attacker's browser works in the victim's. Give each logged-out browser its own random pre-session id in an HttpOnly cookie and bind to that; the example app issues it with the first token and renews it on logout.

The example app combines all three; see `examples/basic` in the repository.

## Where the package and the guide differ

The guide's first recommendation is the `Sec-Fetch-Site` check, then `Origin`, then tokens for legacy browsers. The package offers all three, and its example app applies the stricter combination, because apps that serve a desktop shell send requests that are cross-site by definition and need the allowlist anyway:

- the Origin allowlist always;
- `Sec-Fetch-Site` whenever the browser sends it;
- the token on top.
