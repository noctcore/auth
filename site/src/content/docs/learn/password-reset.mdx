## What goes wrong

Whoever can reset a password owns the account, so the reset flow is a second login form with weaker defences unless it is built as carefully as the first. It can go wrong four ways:

- it can leak which addresses exist;
- its links can be replayed or leak through a `Referer` header;
- two tabs can race the same link;
- a reset that leaves old sessions alive does not remove an intruder who already got in.

## The rule

Treat a reset as a login by mailbox: quiet on the way in, spent once, thorough on the way out.

### The request is uniform and does nothing on the response path

`requestPasswordReset` validates the input, applies the per-IP limit and hands a job to your queue (or runs it detached). The job looks the account up, checks the per-account mail limit (3 an hour) and mails the link. Known and unknown addresses get the same answer in the same time.

### One live token, spent once

A reset link is 32 random bytes, stored only as its SHA-256, valid for an hour. Issuing a new one replaces the old. Applying it runs in this order:

1. **Peek**: look the token up without spending it, so a typo in the new password does not burn the link.
2. **Check** the new password against the policy and the breach check.
3. **Hooks**: run them; a second-factor plugin asks for its code here ([A044](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A044-reset-without-second-factor.test.ts)).
4. **Hash** the new password.
5. **Consume** the token atomically. Of two concurrent resets with the same link, exactly one gets past this step ([A007](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A007-reset-token-reuse.test.ts)).
6. **Write** the new hash.

### Codes become tickets

With `passwordReset.kind: 'code'` the mail carries 8 digits instead. A correct code is exchanged for a ticket valid for 10 minutes, and only the ticket can set the password. The code is checked once and never authorises the write itself. Two caps stand in front of it ([A013](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A013-code-guessing.test.ts)):

| Cap | Default | Counts |
| --- | --- | --- |
| Per code | 5 wrong guesses | At the code that was mailed |
| Per address | 5 guesses per 15 minutes per address | From every network, known address or not, code outstanding or not |

<Aside type="caution" title="The trade-off of the per-address cap">
  Anyone who knows an address can spend those 5 guesses and block code-mode resets for that address
  for 15 minutes. That is the price of stopping guesses spread over many networks. The default link
  mode does not use this cap and is unaffected; apps that choose codes accept the 15-minute nuisance.
</Aside>

### A completed reset cleans up

- **Every session is revoked**, so an intruder who already got in is signed out ([A010](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A010-stolen-cookie-after-password-change.test.ts)).
- **Every outstanding reset token is voided.**
- **The lockout is lifted**: the mailbox was proved.
- **The address is marked verified** unless you turn that off.
- **The owner gets a "password changed" mail.**

No session is issued: the user signs in with the new password.

### Keep the token out of logs and referrers

Put it in the URL fragment or path, not the query string, and serve the page with `Referrer-Policy: no-referrer`.

## Where the package and the guide differ

The guide does not prescribe a reset flow in detail; the package follows the original production flow and adds the stricter pieces:

- no work on the request path;
- peek before consume;
- revocation of every session;
- a mandatory notification mail.

Apps whose invitation logic depends on `emailVerified` can set `passwordReset.markEmailVerified: false`.
