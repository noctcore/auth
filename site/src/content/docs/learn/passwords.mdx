## What goes wrong

People reuse passwords. A table of stored passwords, or of fast hashes of them, is a list of credentials for other sites too: a fast hash like SHA-256 can be tried billions of times a second on a GPU, and most real passwords fall to that within hours.

On the other side, the server pays for every login, so a hash that is slow for the attacker is slow for you as well.

## The rule

Make every guess expensive, check only what helps, and let old hashes upgrade themselves.

### Argon2id, salted, at a measured cost

**Memory is the cost.** Argon2id needs a block of memory per hash, which is what makes GPU and custom hardware attacks expensive.

**Every hash has its own salt.** Each hash gets its own random salt, so equal passwords produce different hashes and precomputed tables are useless.

**The defaults are measured, not guessed.** The defaults are 19 MiB of memory, 3 passes and 1 lane: the memory figure is OWASP's floor, the pass count is the auth guide's. Raise the memory on a box that can afford it, not the passes or lanes.

<Aside type="caution" title="A pepper is not upgraded by a login">
  `argon2id({ secret })` takes an optional pepper, kept outside the database. Changing or losing it
  makes every existing hash unverifiable, and `needsRehash` cannot detect a pepper change, so no
  login can move a hash to a new one.
</Aside>

### Hashes upgrade themselves

Every login that succeeds checks whether the stored hash was made with the current parameters. If not, the password the user just typed is hashed again and stored, as a compare-and-set on the old hash.

<PasswordRehash />

- **A change that lands first wins.** If a password change or reset lands while the new hash is being computed, the upgrade is dropped instead of bringing the old password back ([A015](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A015-rehash-restores-old-password.test.ts)).
- **No migration.** Raising the cost later, or adopting hashes made by an older app, needs no migration and no reset.

### Check length, not composition

A password must be 12 to 256 characters, counted as Unicode code points after NFC normalisation, so the same password typed on two keyboards hashes the same.

There are no "one digit, one symbol" rules: they push people towards predictable patterns without adding much strength. Instead, a new password is checked against known breaches (below).

### Refuse, never repair

Apart from NFC normalisation, input is never trimmed or rewritten. A rejected password gets a reason the user can act on: `weak_password`, `password_too_long` or `breached_password`.

### Ask whether it has leaked

**The password never leaves the server.** The breach check sends only the first five characters of the password's SHA-1 to the Pwned Passwords range API and compares the rest locally. A malformed answer is never read as a verdict ([A022](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A022-breach-response-case-folding.test.ts)).

**An outage does not block sign-ups.** If the service is down, the check fails open: the password is accepted, a warning is logged and the `auth_breach_check{verdict="unavailable"}` metric goes up, so the outage is visible.

### Say why it was unavailable

`pwnedPasswords()` returns a checker with a second method, `check(password)`, that checks exactly like calling it and returns the verdict with its cause. The optional `onResult` option gets the same outcome for every check: clean, breached and unavailable.

Use it to log or count, so a timeout shows apart from a changed response format. An unavailable outcome holds a `reason`:

| `reason`          | When                                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| `timeout`         | No answer within `timeoutMs`, while connecting or reading the body                                       |
| `network-error`   | The request or the body read failed (DNS, TLS, a reset connection)                                       |
| `http-status`     | An answer whose status is not a success; `status` holds the code                                         |
| `unparsable-body` | A success status with a body that is not range lines (an error page, a captive portal, a changed format) |

**An outcome holds nothing secret.** It never carries the password, its hash or the five-character prefix ([A088](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A088-password-material-through-the-breach-outcome.test.ts)).

**The hook cannot change the verdict.** It is not awaited, and the outcome it gets is frozen. A hook that throws or rejects is reported to the checker's `logger` option (silent by default) with the error message only.

### Bound the work

Every door that hashes a password has a rate limit, and an input longer than the policy's maximum is never handed to the hasher at all ([A020](https://github.com/noctcore/auth/blob/main/packages/auth/tests/attacks/A020-oversized-password-dos.test.ts)).

## Where the package and the guide differ

- **Minimum length.** The guide suggests 8 or 10. The package uses 12, from the original production implementation, and refuses a configured minimum below 8.
- **Maximum length.** The guide suggests 50 to 100. The package allows 256, so long passphrases and generated passwords fit; the per-door limits already bound the hashing cost.
- **Character set.** The guide is comfortable limiting passwords to printable ASCII. The package accepts any Unicode and normalises it with NFC, which the guide names as the requirement when Unicode is allowed.
- **Passes.** OWASP's floor is 2 passes at 19 MiB, the guide's is 3 passes at 16 MiB. The package takes the stricter value of each.
