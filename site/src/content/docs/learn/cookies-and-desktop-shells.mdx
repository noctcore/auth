## What goes wrong

The session cookie is the credential, and browsers hand cookies around more freely than people expect:

- **Cookie tossing.** A sibling subdomain, such as a marketing site or a host for user content, can set a cookie for the parent domain that the browser then sends to your app, shadowing or overwriting the real one.
- **Script.** Script injected into a page can read a cookie and send it away.
- **The network.** A cookie sent over plain HTTP can be read on the network.
- **Other sites.** Another site can make the browser send requests with your cookie attached (see [CSRF](/auth/learn/csrf/)).

**Desktop shells add a twist.** An Electron app that serves its pages from its own scheme (`app://`) talks to your API from an origin that is not yours, so its requests are cross-site, and the defaults that protect the web app also keep the cookie away from the shell.

## The rule

Every attribute the browser enforces is on by default, and the shell gets exactly one exception, per origin.

### `__Host-` whenever the cookie is Secure

The session cookie is named `__Host-session` by default. A browser accepts a `__Host-` cookie only if it is `Secure`, has `Path=/` and has no `Domain`, so no subdomain can set or overwrite it.

The trusted-device cookies follow the same rule (`__Host-device`, and `__Host-two-factor-device` with the two-factor plugin), and so do the NestJS and tRPC adapters' CSRF cookies (`__Host-csrf` and `__Host-presession`).

### `Secure` by default, `HttpOnly` always

**`session.cookie.secure` is on by default.** Turn it off only for plain-HTTP local development; that also drops the prefix.

**The session cookie is always `HttpOnly`**, so page script cannot read it. That keeps the token out of an injected script's hands; it does not stop that script from sending requests as the user while the page is open.

### `SameSite=Lax` by default

Cross-site subrequests and form posts carry no session cookie, while a link into the site still does. With the defaults, the session cookie is written as:

```http
Set-Cookie: __Host-session=<token>; Path=/; HttpOnly; Secure; SameSite=Lax
```

| Session              | Cookie lifetime                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Without "remember me" | No `Max-Age`, so the browser drops it when it closes, and the server ends it after 24 hours by default however active it is.                          |
| With "remember me"    | `Max-Age` is the session's remaining life, 30 days by default.                                                                                         |

### Desktop shells: `SameSite` per origin, and `None` only with `Secure`

**`session.cookie.sameSite` also takes a function of the request's `Origin`**, so the web app keeps `Lax` while a shell on its own scheme gets `None` (see [In code](#in-code)).

**Every cookie that travels with the session cookie follows it.** The trusted-device cookies get the same answer, and so do the NestJS and tRPC adapters' CSRF and pre-session cookies and the blank cookie they write to clear a refused session: every cookie that has to travel with the session cookie takes its `SameSite` from the same function, through the core's `resolveSameSite`.

**`None` without `Secure` is refused.** `None` on a cookie that is not `Secure` is refused with a configuration error when `createAuth` starts, for a fixed `sameSite` value. A `sameSite` function cannot be checked without a request, so its `None` without Secure is refused when a cookie is built (usually at the first sign-in).

**The origin is only a hint.** It comes from the request's `Origin` header, which a client that is not a browser can set to anything; that only changes the attributes of its own cookie.

### `None` needs the rest of the CSRF defence

A cookie with `SameSite=None` is sent on requests other sites start too, so the origin it is meant for has to be checked. A shell's requests arrive as `cross-site`, which `verifyFetchSite` refuses by default.

**List the shell's exact origin** in the adapter's `csrf.crossSiteOrigins` (or pass `origin` and `crossSiteOrigins` to `verifyFetchSite` yourself): that origin then passes the `Origin` check, and its `cross-site` requests pass the `Sec-Fetch-Site` check, while every other cross-site request is still refused. The signed double-submit token is still required. [CSRF](/auth/learn/csrf/) covers the trade-off.

**`AuthModule.forRoot` takes the same `csrf.crossSiteOrigins`.** Entries are matched exactly, scheme, host and port; a wildcard, `null` or anything that is not an origin stops the app at boot. The list is empty by default, so nothing changes until you name an origin.

### How a shell gets its CSRF token

The page usually reads the double-submit token from the `csrf` cookie. A shell cannot: its `document.cookie` holds only its own origin's cookies, never `__Host-csrf`, a host-only cookie of the API host. The same holds for a web app on another origin than the API. Its engine still stores the API's cookies and sends them back; only its script cannot read them.

So both adapters return the token from a safe request:

- **NestJS**: `SessionCookies.csrfToken(req, res)` in a `@Public()` GET route, such as `GET /csrf-token` answering `{ csrfToken }`.
- **tRPC**: `ctx.auth.csrfToken()` in a public query, sent with GET through `httpLink` or `httpBatchLink`.

Either returns exactly the token the same response sets or keeps as the cookie, minting the pre-session and the cookie when missing, as any safe request does, and marks the response `Cache-Control: no-store`. The shell keeps the token in memory and echoes it in `x-csrf-token`:

1. **At start**, before its first sign-in, it reads a token bound to its pre-session.
2. **After a sign-in or any rotation**, it uses the token the flow returns (`SessionCookies.set`, `ctx.auth.setSession`), since the old one stops verifying when the new session cookie lands.
3. **After a restart** with a persistent session, its memory and the browser-session cookies are gone but the session cookie is not, so it reads the route again and gets a token bound to that session.

Reading the token from a response grants nothing a cross-site page could use. The token is bound to the session or pre-session it was read for, and the cookie is still required next to it. And whatever your CORS setup lets a page on another origin read (this library configures none, and even a permissive `cors({ origin: true, credentials: true })` changes nothing here), that page's unsafe requests are refused on the `Origin` allowlist and the `Sec-Fetch-Site` check, whatever token they carry. An exempt path mints nothing, so the call refuses there, and it refuses on an unsafe method too. On tRPC it also refuses in a subscription and on a streamed batch, whose headers go out before any procedure runs.

### Keep the token out of every cache

`no-store` only helps if nothing replaces it or answers before it is set. A cached token is still bound to its first caller, so the next caller cannot use it, but it has leaked all the same.

- **tRPC**: tRPC applies your `responseMeta` after the procedures ran, and its headers replace or join the `no-store` the call set (a `Headers` object is appended on the fetch adapter). That is where tRPC's caching recipe puts `s-maxage` on public queries, which is just what the token query looks like, and a CDN or proxy may read its own header from there instead of `Cache-Control`. Wrap your function in `authResponseMeta`, or pass `authResponseMeta()` when you have none: on a response that handed out a token, on the Node and fetch adapters and batched queries included, it drops these headers yours returns, in either form and any case: `Cache-Control`, `Surrogate-Control`, `CDN-Cache-Control`, every `*-CDN-Cache-Control` (such as `Cloudflare-CDN-Cache-Control`), `X-Accel-Expires` and `Edge-Control`. A proxy-specific cache header outside this list is not touched; keep such rules off the token route. Pass it to every tRPC handler you create that serves the token query.

  ```ts
  import { authResponseMeta } from '@noctcore/auth-trpc';

  createHTTPHandler({
    router,
    createContext: (opts) => authContext.node(opts),
    responseMeta: authResponseMeta(appResponseMeta),
  });
  ```

- **nestjs-trpc 2.14.0 and later**: `TRPCModule.forRoot({ trpc: { ... } })` passes the native adapter options, `responseMeta` included, on to tRPC, so wrap yours there: `trpc: { responseMeta: authResponseMeta(appResponseMeta) }`. Its `trpc.middleware` hook runs on the same requests and can set a cache header too: keep it from doing so on the token query.
- **Earlier nestjs-trpc releases**: there is no `responseMeta`, so nothing inside tRPC can replace the `no-store`. Keep any Express or Fastify middleware of yours that sets a cache header off the tRPC base path, or serve the token from the Nest side instead, with `SessionCookies.csrfToken` in a `@Public()` GET route, which the bullet below covers.

- **NestJS**: Nest's `CacheInterceptor` caches GET responses by URL inside the app, and on a hit the handler never runs, so `no-store` never reaches it: every caller gets the first caller's token. Keep the token route out of it (no `@CacheKey` or `@CacheTTL` on it, and skip it in `trackBy` when the interceptor is global through `APP_INTERCEPTOR`) and out of any other response cache, and any interceptor or middleware that sets `Cache-Control` after the handler, which would replace the `no-store`.

<Aside type="caution" title="Never cache the token route">
  Leave the token query or route out of every caching rule, and on tRPC do not wrap only some of
  your handlers in `authResponseMeta`. A cache rule set outside your app (a CDN or proxy
  configured to cache the path, or to ignore the response's cache headers) must skip the path too.
  `authResponseMeta` drops these headers: `Cache-Control`, `Surrogate-Control`, `CDN-Cache-Control`, every `*-CDN-Cache-Control` (such as `Cloudflare-CDN-Cache-Control`), `X-Accel-Expires` and `Edge-Control`. A proxy-specific cache header outside this list is not touched; keep such rules off the token route.
</Aside>

### Limits for shells and other clients

<Aside type="caution" title="Test the shell before relying on None">
  Whether a shell's engine keeps and sends `SameSite=None` cookies to your API depends on the
  engine and its settings. Test the shell against the adapter before relying on it, or load your
  web origin in the shell, where it is an ordinary same-site browser page and needs neither `None`
  nor `crossSiteOrigins`.
</Aside>

`__Host-`, `Secure`, `HttpOnly` and `SameSite` are instructions to a browser. A client that is not a browser, such as a native HTTP library or a command-line tool, keeps cookies wherever its library does and enforces none of them. It must also send an `Origin` the allowlist names, because `verifyRequestOrigin` refuses an unsafe request without one.

## Where the package and the guide differ

The guide asks for `HttpOnly` and `Secure`, and says `SameSite` mitigates many cross-site attacks but is not a complete solution on its own.

- **The package sets all three by default** and adds the `__Host-` prefix, which the guide does not mention.
- **It pairs `SameSite` with the CSRF checks** for the same reason the guide gives.
- **The guide does not cover desktop shells**; the per-origin `SameSite` and the `Origin` allowlist exist for them.
