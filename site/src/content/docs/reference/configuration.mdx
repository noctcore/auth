## Durations

Every time option takes a `Duration`: a number is **seconds**, a string carries its unit, one of `ms`, `s`, `m`, `h` or `d` (`'15m'`, `'1h'`, `'30d'`). One parser reads them all, so a TTL can never be read as milliseconds in one place and seconds in another. Source: `shared/duration.ts`.

## Required

Source: `create-auth.ts` (`assertRequiredConfig`), `crypto/keys.ts`.

<ConfigTable rows={required} />

Any store that passes the conformance suite in `@noctcore/auth/testing` is valid; see [Writing a store adapter](/auth/build/store-adapter/). Flows never await the `mailer`, and each mail is handed over at most once. Keep `secret` apart from your CSRF secret.

### What rotating the secret does

Separate keys are derived from `secret` for code HMACs, trusted-device tokens, session handles and plugins' keyed hashes (such as the two-factor recovery codes), so one key never serves two purposes. Source: `crypto/keys.ts`, `core/plugin-context.ts`.

**Rotating with `previousSecret`.** Deploy the new value in `secret` and the one it replaced in `previousSecret` (a list, newest first, if a second rotation starts before the first ends):

<ConfigTable rows={rotation} />

Every key is derived from each secret too, so these keep verifying during the grace window, while everything new is made under `secret` only:

- outstanding codes and trusted-device cookies;
- session handles: a handle listed before the rotation still revokes its session, and `sessions.list` shows the new handles at once;
- two-factor recovery codes, through the plugins' keyed hashes;
- invitations created before 0.6, which are found through a fallback lookup under their old keyed hash (it tries each previous secret as well) until they expire.

Sessions and invitations created since 0.6 never depend on the secret: an invitation token is stored as a SHA-256, under no key.

Remove `previousSecret` once the longest-lived value has expired: the trusted-device cookie (`throttle.lockout.deviceMaxAge`), and the recovery codes that users made before the rotation, which never expire. Ask every user with a factor to make a new set first, counting from the point where every instance runs the new `secret` (after the second deploy of a rolling deploy; a set made earlier is made under the old secret and stops working when `previousSecret` goes), or accept that their old codes stop working. Leave the key out, or pass `undefined`, when no rotation is under way: an empty string is not "unset", and startup refuses it as shorter than the minimum.

**Rotating without it** invalidates all of the following at once:

- outstanding codes and device cookies;
- every session handle: a client holding an old one gets `{ revoked: false }` and must list again (see [Session handles](/auth/learn/sessions-and-expiry/#session-handles));
- every recovery code of the two-factor plugin, because their HMAC key is derived from the secret: have every user with a factor regenerate their recovery codes;
- invitations created before 0.6, found through a fallback lookup under their old keyed hash until they expire.

Sessions themselves never depend on the secret, so no rotation signs anyone out.

**After a suspected leak, rotate without `previousSecret`**, or keep the window to minutes. While the old secret is configured it is still accepted: whoever holds it can forge device cookies and code HMACs that verify.

**Rolling deploys.** An instance still configured with the old secret alone cannot verify a code, device cookie or handle that an instance on the new one issued, so those fail on it until the roll-out ends. To avoid the gap, deploy twice: first with the current secret in `secret` and the new one in `previousSecret`, so every instance can verify under both, then swap them.

## Password

Source: `password/policy.ts`, `password/breach.ts`, `create-auth.ts`. Why these defaults: [Passwords](/auth/learn/passwords/).

<ConfigTable rows={password} />

**The minimum is stricter than the auth guide's** 8 or 10.

**Length** is counted in Unicode code points of the NFC form, so the same password typed on a phone and a desktop has the same length.

**No composition rules** ("one digit, one symbol"): they push people toward predictable patterns, as NIST SP 800-63B notes, and the breach check does the job they were meant to do.

**The breach check.** `false` or leaving it out runs no check. The check fails open: an outage accepts the password and is logged, counted and written to the audit trail as `password.breach_check_unavailable`. Only the first five hex characters of the password's SHA-1 leave the server.

### `pwnedPasswords(options)`

<ConfigTable rows={pwnedPasswordsOptions} prefix="pwnedpasswords" label="Option" />

`onResult` is called with every outcome (`{ verdict, reason?, status? }`) to log or count it; it is not awaited, cannot change the verdict, and a throw is reported to `logger`. The checker's `check(password)` returns the same outcome. Outcomes never carry the password, its hash or the prefix. The reasons are listed in [Passwords](/auth/learn/passwords/).

## Session

The `session` key takes the session options and two more keys, `cookie` and `freshAuthAge`. Source: `session/session-types.ts`, `session/session-manager.ts`, `flows/resolve-settings.ts`. Why these defaults: [Sessions and expiry](/auth/learn/sessions-and-expiry/).

<ConfigTable rows={session} />

**`absoluteTtl`** bounds what a stolen cookie is worth.

**`rememberMeTtl`** must not exceed the session store's `maxSessionTtlMs` (the Redis store's `maxSessionTtl`, also 30 days by default).

**`idleTimeout`** also accepts a function of `{ rememberMe, attributes }`, decided per session at sign-in. Its value must be longer than `touchInterval`, like a fixed one: otherwise a session in steady use is never touched and expires as idle while its user is active. The startup check cannot see a function's values, so the sign-in that gets a value no longer than `touchInterval` throws an `AuthConfigError` before any session is written.

**`touchInterval`**: last-active is written at most once a minute instead of on every request.

**`attributes`**: the schema makes a corrupt or old record refused, not trusted.

### Evictions at the cap

The oldest sessions beyond `session.maxPerUser` are evicted after the new one is written, so concurrent sign-ins converge on the cap. They are picked by creation time, then by id, and never include the session being issued, even when its creation time ties an older one or its instance's clock is behind. A session written while the sign-in ran is evicted only if it sorts before the new one, so two sign-ins racing at a cap of one leave exactly one. A sign-in that stalls before its write can leave one session over the cap until the next sign-in, and sign-ins on instances whose clocks disagree can, rarely, evict each other. Each sign-in reads the user's sessions once more, before its write, when a cap is set.

- The issued session lists the evicted sessions' handles in `evictedHandles` (safe for a client) and their store keys in `evicted` (server-side only).
- `onSessionsRevoked` hears of them with reason `evicted`, so you can close their sockets and drop their caches.
- Each eviction is reported once, even when sign-ins race at the cap or race a sign-out of the same session, provided the session store's `delete` returns the ids it removed (the memory and Redis stores do).

### Fresh authentication

`session.freshAuthAge` is how recent a credential proof must be to revoke another session or every other session, so a stolen session cannot sign the owner out.

- The library's own doors (revoking devices, second-factor enrollment, step-up) read it from the live session in the store.
- Your own routes can ask for it with `auth.requireFreshAuth(session)`, which checks the object you pass, so pass the session `validateRequest` just returned.
- Plugins have `context.requireFreshLiveSession(session)`, which re-reads it.

### Session cookie

Source: `http/cookie.ts`. Why these defaults: [Cookies and desktop shells](/auth/learn/cookies-and-desktop-shells/).

<ConfigTable rows={sessionCookie} />

**`name`.** When the cookie is Secure the name becomes `__Host-session`: the browser then requires Secure, `Path=/` and no `Domain`, so a sibling subdomain cannot set or overwrite it.

**`secure: false`** also drops the `__Host-` prefix from the device cookie (`device` instead of `__Host-device`).

**`sameSite`** accepts a function of the request's `Origin`, for an app that also serves a desktop shell. The trusted-device cookies and the NestJS and tRPC adapters' CSRF, pre-session and blank session cookies get the same answer.

<Aside type="caution" title="SameSite none needs Secure">
A fixed `'none'` without Secure is refused when `createAuth` starts, while a function's `'none'` without Secure is refused when a cookie is built.
</Aside>

The cookie is always HttpOnly. A session without "remember me" gets a browser-session cookie (no `Max-Age`).

## Email addresses

Source: `shared/email.ts`. Why the default: [Email and requests](/auth/learn/design-choices/#email-and-requests) in the design choices.

<ConfigTable rows={email} />

The policy applies everywhere: every flow and plugin, and `auth.normalizeEmail`.

### The built-in policies

| Policy | What it does |
| --- | --- |
| `'standard'` | Trims, lowercases A to Z and refuses any non-ASCII character (`invalid_email`), so Unicode case folding can never merge two addresses. |
| `'ascii'` | Stores the same spelling as `'standard'`, but answers a non-ASCII address with `email_not_ascii`, so you can say why. |
| `'unicode'` | Keeps Unicode addresses: NFC, then lowercase of the domain and the local part. The details follow. |

**`'unicode'` folds the local part too.** The Greek final sigma is folded to the plain one in the local part only (a domain keeps a typed final sigma, which IDNA2008 treats as its own letter, while a capital sigma lowercases to the plain one). No mainstream provider treats the local part as case-sensitive, and folding it stops case-collision takeovers.

**`'unicode'` refuses** invisible, bidi, control and compatibility characters (fullwidth letters, ligatures), punycode labels (send the Unicode form), any part that mixes scripts, apart from the Chinese, Japanese and Korean mixes with Latin, and the Latin letters that read as other Latin ones it knows about: the dotless i, the IPA Extensions block (U+0250 to U+02AF) and a combining dot above on i or j.

**`'unicode'` domains** also have no port, path, query, fragment, credentials or percent escape. Every label of the domain's ASCII (punycode) form is letters, digits and inner hyphens (at most 63) and decodes back to exactly the label typed, so nothing UTS 46 would remap is accepted (an ideographic full stop for a dot, a Greek iota subscript, an old Cyrillic letter form, `127.1`).

<Aside type="caution" title="What 'unicode' does not catch">
It has no UTS 39 confusables check, so an address written wholly in another script, or with another same-script lookalike, is a different, valid account; the verification mail is the backstop. Acceptance under `'unicode'` also depends on the runtime's URL parser and Unicode tables (Node, Bun, an edge runtime): uniqueness holds on one runtime, but an address stored under one runtime can be refused after a runtime upgrade that remaps one of its characters.
</Aside>

### What every policy refuses

- An address with whitespace, a control character or an RFC 5322 special besides the one `@` (`, ; : < > ( ) " \ [ ]`): an address parser must read it as one plain mailbox.
- A domain that is not a host name. Every built-in policy takes only letters, digits and inner hyphens per label, at most 63, no empty label, and a last label that is not all digits, so `exa_mple.com`, `-example.com`, `example..com` and an IPv4 address such as `127.0.0.1` or `127.1` are refused.

**Surrounding whitespace.** Every policy trims with `String.prototype.trim`, which also strips Unicode whitespace (a no-break space, an ideographic space) around the address, not only ASCII spaces and tabs. `ascii` trims exactly like `standard`, so the two always store the same spelling.

### A custom normaliser

Or pass `(email) => string | null`, your own normaliser. Return `null` for an address you refuse; it is answered `invalid_email`. Refusing whole domains is fine.

**It must be pure, deterministic and idempotent**: `normalize(normalize(x)) === normalize(x)`, because a stored address is normalised again every time it is compared.

**Its result** must be `null` or an address of at most 254 bytes with exactly one `@`, a non-empty local part and domain, and no whitespace, control characters or RFC 5322 specials (`, ; : < > ( ) " \ [ ]`; the address goes into mail headers). A normaliser that passes a quoted local part such as `"quoted"@example.com` through fails the startup check.

**`createAuth` tests it at startup** over a sample of addresses (mixed case, IDN, decomposed accents, confusables, junk) and refuses to start if it throws, returns anything else, answers differently twice, is not idempotent, or gives the same result for different mailboxes it accepts (`alice@example.com` and `bob@example.com`, or one local part at two domains), so a constant or domain-only normaliser fails at startup.

**On each call** an address whose result is unusable or not a fixed point is refused and logged. When it throws, the address is refused and the log line carries only the error's class name (`errorName`), never its message, which could quote the address.

### Living with the policy

**Lookups are exact.** The core treats a user row whose stored address is not exactly the one it asked for as not found, so a store whose lookup goes through a case- or accent-insensitive collation cannot hand one account to several spellings. Prefer a binary or accent-sensitive collation on the email column anyway; see the Prisma adapter's README.

**Use the same normaliser in your own code.** `auth.normalizeEmail(email)` gives the configured spelling, or `null`. Call it wherever your app stores or looks up an address outside the flows (an admin create, an import, an SSO first login), never a fixed function. The exported `normalizeEmail` is the `standard` policy only.

<Aside type="caution" title="Changing the policy needs a data migration">
Rows are stored in the spelling of the policy that wrote them. Before switching `email.normalize` on a live database, rewrite every stored address (users, pending invitations, and any address in outstanding tokens, or let those expire) into the new spelling, and resolve the duplicates that rewrite may reveal (two rows that become one address). The package does not do this for you. Until it is done, owners of rows the new policy no longer matches cannot sign in or reset by address, and a sign-up can create a second account for the same mailbox.
</Aside>

**Upgrading: check rows written outside the flows.** Lookups by address are exact, whatever the policy: a user row whose stored email is not exactly what the normaliser produces counts as not found. A row written by an import, an admin tool or a seed in another spelling (uppercase letters, surrounding whitespace, a non-ASCII character under the default policy) is unreachable even if you never change `email.normalize`.

Before upgrading, find the rows where the stored email differs from `auth.normalizeEmail(email)`, then rewrite them or merge the duplicates. Each time the store returns such a row for a lookup, the core logs a warning with the user id (never the address), so rows you missed show up in your logs. Behind a case- or accent-insensitive collation that warning repeats on every lookup of such a row and can be noisy; rewrite the rows or make the column binary to silence it.

**Upgrading: domains that are not host names.** The `standard` and `ascii` policies take only a host name as the domain, as `unicode` does: letters, digits and inner hyphens per label (at most 63), no empty label, and a last label that is not all digits. They used to check only for one inner dot, so a stored address whose domain is an IPv4 address (`127.0.0.1`, `127.1`), has an underscore or another character outside a host name, or a label that is empty, starts or ends with a hyphen or is longer than 63 is now refused: its owner can no longer sign in, reset or be found by address, and a pending invitation to it cannot be accepted.

An outstanding email change or verification token that names such an address can no longer be redeemed either: the flows normalise the address again when the token is used and refuse it (they fail closed), so the user has to start the change or request a new mail with a valid address. Find such rows before upgrading and rewrite or remove them. In PostgreSQL:

```sql
SELECT id, email FROM users -- your user table
WHERE split_part(email, '@', 2) !~ '^([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$'
   OR split_part(email, '@', 2) ~ '\.[0-9]+$';

SELECT id, email FROM "AuthInvitation"
WHERE split_part(email, '@', 2) !~ '^([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$'
   OR split_part(email, '@', 2) ~ '\.[0-9]+$';
```

On another store, run the check above in your own code: every row where `auth.normalizeEmail(email)` is not exactly the stored email, which also finds these.

## Throttle

Two keys: `throttle.lockout` for the login lockout, `throttle.doors` for the per-door rate limits. Each rule is `{ limit, window }`; a part you leave out keeps its default.

### Lockout

The login lockout. Source: `throttle/rules.ts`, `throttle/throttle.ts`; the reasoning is in [Brute force and lockout](/auth/learn/brute-force-and-lockout/).

<ConfigTable rows={lockout} />

**No permanent lock by default.** `maxLock` caps every temporary lock, and there is no permanent lock unless you opt into `permanent`, because a permanent lock lets an attacker lock the owner out.

**Device cookies.** Holding many device cookies adds no guesses: `perDevice` is also the budget all of an account's devices share.

**Session doors.** `reauthenticate` and `changePassword` spend these same budgets: `perAccountIp` and `perAccount` while the account is unlocked, and under a lock the live session counts as one more device in `perDevice`. Guesses through login and both doors add up. A correct proof while the account is unlocked still counts toward `perAccount` (success returns only the `perAccountIp` slot, as at login), so an app that asks for re-authentication very often can lock its own user and send a lock notice; with `countSuccesses: false` the correct proof hands its `perAccount` slot back at once, since the caller already holds a session. Under a lock, a stolen session can spend the `perDevice` budget shared by every device of the account, which refuses the owner's device cookie until the lock ends; a password reset clears the lock and ends every session. Second-factor codes have their own budget and do not draw on these.

**`deviceMaxAge`** must be at least a minute shorter than the session store's `epochTtlMs` (the Redis store's `epochTtl`, 90 days by default). A device cookie is revoked only by the user's revocation epoch, and a store that forgets an epoch reads it as 0 again, so a cookie revoked by a sign-out everywhere would verify once more after the lapse. The minute is the clock skew a cookie is allowed: its issue time comes from the server that set it, which may run ahead, so equal values are refused too.

**`revealLocked`.** Unknown addresses lock and answer the same, but the answer tells anyone that the address is locked and when it lifts: an enumeration signal the generic answer does not give. Pair it with a captcha and per-IP rate limits.

#### Lock durations

By default a lock lasts `baseLock`, multiplied for each lock in a row and capped at `maxLock`. `durations` replaces both with a ladder you write out: the first lock in a row lasts the first entry, the next the second, and once the list runs out every further lock lasts the last entry. `['15m', '1h']` locks for 15 minutes, then an hour each time after, until `quietPeriod` passes with no new lock and the ladder starts over. The two-factor plugin's factor locks share the password lockout's backoff, so they climb the same ladder (in their own count). Startup refuses an empty list, an entry that is not a duration or is zero, and `durations` together with `baseLock` or `maxLock`, since one of them would be ignored.

#### Counting successes

By default a correct password spends a slot of `perAccount` like a wrong one: only its own source's slot (`perAccountIp`, or a device's) comes back. A user who signs in many times within the window, from several devices or a script, can lock their own account.

With `countSuccesses: false` the `perAccount` slot comes back too, so only failures count. It comes back when the sign-in completes (its session is issued with `via: 'password'` or `via: 'second-factor'`, every factor proved), not when the password proves right: a correct password that opens a second-factor challenge keeps spending until the factor is proved. At `reauthenticate` and `changePassword` it comes back right after the correct password. A completion hands back at most one slot, and never more slots than correct passwords reserved in the current window, however many sign-ins complete at once. Refunds are capped per window and matched by count, not to the attempt that earned them: a completion that reserved nothing of its own (a challenge opened in an earlier window, a device sign-in) can take a slot another correct password in the window is owed. Slots owed in a window that ended, a lock included, never come back in the next. Not atomic: a completion racing the first attempt of a new window, or racing a password reset, can hand back one slot of the new budget.

The trade-off: an attacker who also holds the password could sign in between guesses to win budget back. That only matters together with a second factor, and there the slot comes back only once the factor is proved.

#### The permanent tier

`throttle.lockout.permanent` takes `{ afterLocks, trustedDevices? }`.

- **When it locks.** After `afterLocks` temporary locks in a row (each within `quietPeriod` of the last; a completed sign-in or a completed password reset resets the count), the next lock holds until an admin calls `auth.lockout.clear`. The count takes password locks and the two-factor plugin's factor locks alike. A sign-in completes when its session is issued with `via: 'password'` or `via: 'second-factor'` (every factor proved); a correct password with a second factor still owed, or at `reauthenticate` or `changePassword`, does not reset it. A password reset does not lift it. `afterLocks` must be a whole number of at least 1.
- **What it locks.** For an address with an account the lock is kept under the user id, so it follows the account through an email change, and it ends the account's sessions. For an address with no account it is kept under the address, and a sign-up on that address clears it.
- **Turning it off later** stops login reading its marker, but `auth.lockout.inspect` still reports a leftover permanent lock until `auth.lockout.clear` lifts it.

<Aside type="caution" title="Anyone who knows an address can lock its owner out">
The permanent tier is a denial of service anyone can trigger on purpose. Pair it with a captcha and per-IP rate limits.
</Aside>

**`trustedDevices: true`** (the default): the lock deletes the account's sessions but keeps its device cookies, so the owner can still sign in from a known device with the usual device budgets. A session from such a sign-in may reauthenticate and change the password, but no session may change the email. Other ways in still mint a session in this mode, each needing a correct password or your SSO: an app's SSO through `issueSession`, a two-factor challenge started before the lock, and a login racing the revocation. The default mode adds no read per request.

**`trustedDevices: false`**: the lock bumps the revocation epoch (every session and device cookie ends) and refuses every session door (issuing a session by any path, validating one, reauthentication, password change, email change, email verification) until an admin clears it. Because validation checks the lock, a session the background revocation failed to end is refused, and revoked, on its next request.

#### Inspecting and clearing locks

- `auth.lockout.inspect({ email })` or `({ userId })` returns `{ locked, permanent, until }` for an address.
- `auth.lockout.clear({ email | userId, meta })` lifts every lock on it, the permanent one included, resets its backoff, returns the state it found and writes an `account.lock_cleared` audit row. The clear is not atomic: a burst of failures running during it can lock the account again as soon as it is lifted.
- Both answer for any address, known or not, so expose them only on admin routes.
- The `onPermanentLock` hook (`{ userId, email, meta }`) runs off the response path when the permanent tier locks an account, after its sessions end (`onSessionsRevoked` hears `locked-permanently`), beside the `account.locked_permanently` audit row and a `lockout` mail with `permanent: true`.

Source: `flows/lockout-admin.ts`, `flows/lock-notice.ts`.

#### Counting your own proofs

For a proof your app checks itself (its own second factor, a PIN), outside login's gate:

- `auth.context.recordFailedProof({ userId | email, meta })` counts a failure in the address's account-wide budget, the one login spends. A lock it sets is carried out like a password lock (the `lockout` mail, the `account.locked` audit row and, in the permanent tier, the end of the sessions and `onPermanentLock`), off the response path, and counts toward the permanent tier. It returns `{ newLock? }`. An address with no account counts the same and nobody is told. Pass only the account the request is already acting on (the user of its session or challenge): it locks whatever account it is pointed at, so a target taken from the request body lets anyone lock any account.
- `auth.context.escalateLock({ userId, meta })`, for a proof with its own budget and lock: call it once for each new lock it sets. With `permanent` on, the lock counts toward the tier in the same count as the password locks, and a permanent lock is carried out the same way. It does nothing while `permanent` is off.
- `auth.context.throttle.recordFailure` only counts: a lock reached through it sends nothing. Prefer `recordFailedProof`.

Source: `core/auth-core.ts`, `core/plugin-context.ts`.

### Door limits

`throttle.doors` overrides the per-door rate limits, each a `{ limit, window }` rule. Doors are keyed by client IP unless noted. Every limit fails closed: a counter store that cannot answer refuses the request. Source: `DEFAULT_DOOR_LIMITS` in `core/config.ts`.

<ConfigTable rows={doors} prefix="throttle-doors" label="Door" third="Keyed by" />

**Mail budgets are spent before the mail is handed over.** `password-reset-mail`, `email-verification-request` and `email-change-request` count a request even when its mail is then dropped or fails (see [Mail](/auth/build/mail/#a-dropped-or-failed-mail-still-spends-the-budget)).

**The per-address door has a trade-off**: anyone who knows an address can spend its budget and block that address's code-mode reset for 15 minutes. Link-mode reset, the default, does not use it.

### What the hooks do

Functions the flows call at fixed points, such as `sessionAttributes`, `beforeSessionCreate`, `beforePasswordReset`, `beforeEmailChange`, `afterRegister` and `onPermanentLock`. A hook can refuse with `refuse(code, reason)`.

- **`passwordResetRequirements`** says ahead of time what applying a reset will ask for, as `{ secondFactor?: boolean }` for `{ user }`, so `inspectPasswordReset` can tell a reset page to show the code field. Answer `secondFactor: true` when your own `beforePasswordReset` hook will demand a code for that user; the two-factor plugin answers it for a confirmed factor. Any hook's `true` wins. For an account your `beforePasswordReset` always refuses (one your app closed), return the same `refuse(...)` here, so the check answers what the reset would; the core does this for an account in an email revert lockout. It must only read: it runs on every inspection, which spends nothing.
- **`afterRegister`** is awaited and runs only for a new address, so its time shows in sign-up timing: queue slow work instead of awaiting it.
- **`onSessionsRevoked`** hears of every session that ends by a flow, with its reason (`logout`, `revoke-all`, `evicted` for the per-user cap, and so on), as `{ userId, sessionIds, sessionHandles, reason, scope? }`. `sessionIds` are store keys for server-side use only, `sessionHandles` the same sessions' public handles, as `sessions.list` showed them. An error it throws is logged and never fails the flow. It is awaited on the response path, on sign-in too when the cap evicts, so keep it fast and queue slow work instead of awaiting it.
- **`sessionStanding`** runs on every validated request, after `onSessionValidate` accepted it, and returns a standing that `validateRequest` attaches to the session for that request only (the two-factor plugin's `twoFactor`: `grace` or `enrollment-only`). A standing never widens access, so an `enrollment-only` from any hook wins over a `grace`. Keep it cheap.

## Adapter options

The adapters take their own options beside the `createAuth` result; the guides cover them ([NestJS](/auth/build/nestjs/), [tRPC](/auth/build/trpc/)). The ones below tie in with keys on this page. Source: `auth-nestjs/src/options.ts`, `auth-trpc/src/options.ts`, `session/session-manager.ts`.

### Counting activity: `touch`

`session.touchInterval` says how often last-active may be written; `touch` decides which requests may write it at all. A request that counts as activity refreshes last-active at most once per `touchInterval`. A passive one (a poll on a timer) is validated and answered with its session as usual, but never refreshes last-active, so an idle session still expires while only polls arrive. The core's `validateRequest` takes the same switch as `touch: false`. Anything but a boolean or a function stops the boot with an `AuthConfigError`. Background: [Background polls](/auth/learn/sessions-and-expiry/#background-polls).

#### `AuthModule.forRoot(options)`

<ConfigTable rows={nestjsAdapterOptions} prefix="nestjs-authmodule" label="Option" />

The predicate runs before the middleware validates the session and cannot read route decorators. Under nestjs-trpc the tRPC context validates it a second time, with its own switch (see [Use with tRPC](/auth/build/trpc/#background-polls)). Its `path` is the raw request path with the global prefix and without the query string: it is not normalised, so a trailing slash or a different case is a different path, and a predicate that compares it should normalise first. See [Use with NestJS](/auth/build/nestjs/#background-polls).

#### `createAuthContext(options)`

<ConfigTable rows={trpcAdapterOptions} prefix="trpc-createauthcontext" label="Option" />

The predicate and the meta are read from the calls tRPC parsed before it built the context. When tRPC names no call, the request touches. With nestjs-trpc and `AuthModule` mounted, the session is validated by both, and a poll is passive only when marked in both; see [Use with tRPC](/auth/build/trpc/#background-polls) for that and the other cases where this has no effect.

### Handing out the CSRF token

For a client that cannot read the `csrf` cookie. The token is the one the adapter already set as the cookie on that response, bound to the same session or pre-session. Source: `auth-nestjs/src/session-cookies.ts`, `auth-trpc/src/context.ts`, `auth-trpc/src/response-meta.ts`.

<ConfigTable rows={csrfHandout} prefix="csrf-handout" label="Call" third="What it does" />

`authResponseMeta` drops `Cache-Control`, `Surrogate-Control`, `CDN-Cache-Control`, every `*-CDN-Cache-Control`, `X-Accel-Expires` and `Edge-Control` from the headers your `responseMeta` returns, only on a response that handed out a token; any other response gets your answer unchanged. Other proxy-specific cache headers are left alone, so keep such rules off the token route.

### For adapter authors: the CSRF layer

Both adapters run one CSRF implementation from `@noctcore/auth`, so an adapter of your own (another framework, another tRPC transport) can give the same answers for the same cookies. These exports are public API, checked by the API snapshot and versioned like the rest of the core:

- `resolveCsrfSettings(input, secure)`: the boot checks (the options present and of their type, lists without empty slots, at least one secret of 32 bytes, exact `crossSiteOrigins`, a non-empty allowlist, a valid header name) and the cookie names, `__Host-` prefixed when `secure`.
- `readCsrfCookies(csrf, cookieHeader)`: the pre-session id and the CSRF cookie from the `Cookie` header.
- `csrfRequestAllowed(csrf, request)`: the verdict on a request judged as unsafe (Origin allowlist, `Sec-Fetch-Site`, the signed double-submit token). Your adapter decides which requests it judges.
- `handOutCsrfToken(options, request)`: what a safe request sets, and the token to hand to a client that cannot read the cookie.
- `bindCsrfToSession(options, session, sameSite)` and `startCsrfPreSession(options, sameSite)`: the CSRF cookie to write with a new session, and the fresh pre-session after one ends.
- `appendSetCookie(res, spec)`: adds a `Set-Cookie` header to a Node-style response without dropping the ones already set.
- `isSafeMethod(method)`: the methods that skip the check (GET, HEAD, OPTIONS, ASCII case folding only).

Source: `auth/src/http/csrf-adapter.ts`. Background: [CSRF](/auth/learn/csrf/).

## Startup checks

`createAuth` throws an `AuthConfigError` when:

- a store, `password.hasher` or `mailer` is missing, or `secret` is missing or neither a string nor bytes;
- `password.breachCheck` is neither a breach checker (a function, such as `pwnedPasswords()`) nor `false`, or `captcha` is not a verifier with a `verify` function (a string such as `"false"` from the environment used to count as configured and throw on the first sign-up or login);
- `password.policy.minLength` is below 8 or not a whole number, or `password.policy.maxLength` is not a whole number of at least `minLength`;
- `session.cookie.name` is not a string, or has characters other than letters, digits, `_` and `-`;
- `session.cookie.secure` is not `true` or `false`;
- `session.cookie.sameSite` is a fixed `'none'` while `session.cookie.secure` is `false`;
- `session.cookie.sameSite` is a fixed value other than `'lax'`, `'strict'` or `'none'` (`'None'` used to skip the check above; a function's value is checked the same way when a cookie is built);
- `session.attributes` has no `parse` function;
- `session.maxPerUser` is not a positive integer or `null`;
- `session.touchInterval` is not shorter than a fixed `idleTimeout` (an `idleTimeout` function is checked at each sign-in instead, see [Session](#session));
- `session.absoluteTtl` or `rememberMeTtl` is longer than the session store's `maxSessionTtlMs`;
- `throttle.lockout.deviceMaxAge`, or the two-factor plugin's `trustedDevices.ttl`, plus a minute of clock skew is longer than the session store's `epochTtlMs`, or the store declares `epochTtlMs` or `maxSessionTtlMs` as anything but a positive number;
- `email.normalize` is an unknown name, or a custom normaliser fails its startup test;
- `registration.revealExisting`, `registration.autoLogin` or `passwordReset.markEmailVerified` is not `true` or `false`;
- `registration.autoLogin` is set without `revealExisting`;
- `emailVerification.kind`, `passwordReset.kind` or `emailChange.kind` is not `'code'` or `'link'` (a typo such as `'Link'` used to read as the other kind);
- a `urls` entry or `passwordReset.enqueue` is not a function, or link verification, link reset or link email change is chosen without its `urls` function;
- a duration option does not parse (`'15 min'`, `NaN`, a negative number): every `ttl`, `passwordReset.ticketTtl`, `emailChange.revertTtl` and `blockAfterRevert`, `session.freshAuthAge`, `absoluteTtl`, `rememberMeTtl`, `touchInterval` and a fixed `idleTimeout`, the `throttle.lockout` durations and rule windows, and `background.timeout`. The error names the key;
- `emailVerification.linkWithoutSession` is set without `kind: 'link'`, or is not `true` or `false`;
- `emailVerification.digits`, `passwordReset.digits` or `emailChange.digits` is outside 6 to 9;
- `emailVerification.maxAttempts`, `passwordReset.maxAttempts` or `emailChange.maxAttempts` is not a whole number of at least 1;
- `emailChange.revertTtl` is shorter than 7 days;
- a rule under `throttle.lockout` (`perAccountIp`, `perAccount`, `perDevice`) is not an object, or a `limit` under it or `throttle.doors` is not a whole number of at least 1, or its `window` is zero (a door rule also needs a `limit` and a valid `window`; a `null` door rule, and a `null` `throttle.lockout`, keep the defaults);
- `throttle.lockout.baseLock` or `throttle.lockout.maxLock` is zero;
- `throttle.lockout.durations` is not a list, is empty, has an entry that is not a duration or is zero, or is set together with `baseLock` or `maxLock`;
- `throttle.lockout.revealLocked` or `throttle.lockout.permanent.trustedDevices` is not `true` or `false`;
- `throttle.lockout.countSuccesses` is not `true` or `false`;
- `throttle.lockout.permanent.afterLocks` is not a whole number of at least 1;
- `previousSecret` holds a value that is not a string or bytes, is shorter than the minimum for `secret`, or repeats `secret` or another previous secret (an empty string counts as shorter), or is a list with an empty slot;
- `plugins` is not a list, holds an empty slot or an entry that is not a plugin with an `id`, a plugin's `flows` is not a function or its `requires` is not a list;
- a plugin requires `captcha` and none is configured;
- `background.timeout` is zero, `background.maxPending` is not a whole number of at least 1, or `background.waitUntil` is not a function.

Sources: `create-auth.ts`, `plugins/two-factor/index.ts`, `core/background.ts`, `flows/resolve-settings.ts`, `session/session-manager.ts`, `http/cookie.ts`, `shared/email.ts`, `shared/config-checks.ts`, `throttle/throttle.ts`, `throttle/rules.ts`, `core/plugins.ts`, `crypto/keys.ts`; for the plugins, their `options.ts`; for the factories, `password/argon2.ts`, `password/breach.ts` and `http/turnstile.ts`.

A list option has to be a real list with no empty slot: a single string would be read character by character, and an empty slot (`[, '/x']`) is skipped by the checks that walk a list but read as `undefined` later. A boolean option has to be a real `true` or `false`, and a count a real number: a value read from the environment as the string `"false"`, or as `Number(undefined)` (`NaN`), is refused rather than read as on or as no limit. Convert it first, for example `process.env.REVEAL_EXISTING === 'true'`. Leaving a key out, or passing `undefined` or `null`, still gives its default, also for `password.policy.minLength` and `maxLength`.

The plugins check their own options the same way when they are created: `invitations` refuses an `acceptWithoutSession` or `recheckInviter` that is not `true` or `false` and a `ttl` or rule `window` that does not parse; `membership` a `revokeSessionsOnChange` that is not `true` or `false`, a `canManage` that is not a function and an `adminRoles` with an empty slot; and `twoFactor` a `trustedDevices` that is neither `false` nor an object, a `required` or `enforcement` that is not a function, and a `stepUpWindow`, `trustedDevices.ttl` or rule `window` that does not parse (a `null` `required`, `enforcement` or `importedRecoveryCodes` counts as left out).

The collaborators you build with a factory check theirs when called: `argon2id()` refuses an `unsafeAllowWeakParameters` that is not `true` or `false`, a `memoryCost`, `timeCost` or `parallelism` that is not a whole number of at least 1, and a `secret` that is not bytes; `turnstile()` a missing or empty `secret`, an `expectedHostnames` that is not a list of strings (one string was matched as a substring, so any part of the host name passed), a `checkAction` that is not `true` or `false`, a `timeoutMs` that is not a number above zero, and a `fetch` or `onResult` that is not a function; `pwnedPasswords()` the same for `timeoutMs`, `fetch` and `onResult`, and a `userAgent` or `baseUrl` that is not a string.

Source: `packages/auth-prisma/src/user-store.ts`, `index.ts`.

<ConfigTable rows={prismaStoresOptions} prefix="prismastores" label="Option" />

#### Accounts your app closed

The store guards its reads and writes with `deletedAt` only. An app that closes an account to new credentials on a column of its own (a member removed from an organisation who keeps the row and the address, say) can refuse such an account in a `beforePasswordReset` hook, but the hook runs before the token is spent and the hash is written, so an account closed in between would still get the new password. `writeWhere` puts the app's condition in the same UPDATE as the write:

```ts
const { users, tokens } = prismaStores({
  delegate: prisma.user,
  tokenDelegate: prisma.authToken,
  writeWhere: { closedAt: null },
});
```

A closed row then refuses `setPasswordHash`, `markEmailVerified` and `changeEmail`, and the flows answer that like any refused write: `resetPassword` answers `invalid_token`, `changePassword` answers `session_expired`, an email change answers as stale. The condition is combined with the store's own through `AND`, so it can narrow a write but never widen it. Startup refuses a `writeWhere` that is not an object.

What it leaves alone:

- **Reads.** Lookups still find the row, so login works for a closed account unless your hooks refuse it (`beforeSessionCreate`, say). Refuse it there too.
- **An email revert** (the `changeEmail` that also clears the password). It only takes access away, so the owner of the old address can still undo a change on a closed account.
- **Rehash after login.** It is guarded like any password write, so a closed account keeps its old hash; the login itself is not affected.
