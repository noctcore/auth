# @noctcore/auth-trpc

## 0.7.0

### Minor Changes

- [#134](https://github.com/noctcore/auth/pull/134) [`eb87941`](https://github.com/noctcore/auth/commit/eb8794111d0d893fa4473aa0703a978b4af15059) Thanks [@Shironex](https://github.com/Shironex)! - Both adapters can now validate a request without counting it as activity, so a page that polls on a timer no longer keeps an idle session alive for its whole absolute lifetime. The default is unchanged: every request touches.
  
  - NestJS: a new `touch` option on `AuthModule`, `true`, `false` or a predicate `(request) => boolean` over the request's method, path (a global prefix included, no query string) and headers. It runs before the one validation of the request. A request it marks passive is answered with its session and leaves `lastActiveAt` alone. New exported type `TouchRequest`.
  - tRPC: a new `touch` option on `createAuthContext`, `true`, `false` or a predicate `(path) => boolean` asked about each procedure path of the request, and a procedure meta `touch: false` (on `AuthProcedureMeta`). Both are read from the calls tRPC parsed before it built the context. A batch touches when any of its procedures is active, and a request whose adapter names no calls touches as before.
  - The CSRF checks and the guards' decisions do not change with the option, and the session is still validated once per request.

- [#135](https://github.com/noctcore/auth/pull/135) [`f4f0852`](https://github.com/noctcore/auth/commit/f4f085256879f203a3ebb998695de571d7cf57ab) Thanks [@Shironex](https://github.com/Shironex)! - Both adapters now hand the CSRF token to a client that cannot read the API's cookies, such as a desktop shell on its own scheme or a web app on another origin than the API. Until now such a client had no token for its first sign-in, nor for any unsafe request after a restart with a persistent session.
  
  - NestJS: `SessionCookies.csrfToken(request, response)` returns `{ csrfToken }` for a `@Public()` GET route (for example `GET /csrf-token`). It is exactly the token `CsrfMiddleware` set or kept as the `csrf` cookie on that response, minting the pre-session and the cookie when missing, and it marks the response `Cache-Control: no-store`. It throws an `AuthConfigError` on an exempt path (which still mints nothing) and on an unsafe method.
  - tRPC: `ctx.auth.csrfToken()` returns `{ csrfToken }` in a public query sent with GET, with the same guarantees. It throws an `AuthConfigError` on a request with an unsafe method, on a streamed batch (`httpBatchStreamLink`) and in a subscription.
  - tRPC: `authResponseMeta(responseMeta)` wraps the app's `responseMeta` (or stands alone as `authResponseMeta()`) and keeps `Cache-Control: no-store` on every response that handed out a token, dropping these headers the app returned: `Cache-Control`, `Surrogate-Control`, `CDN-Cache-Control`, every `*-CDN-Cache-Control` (such as `Cloudflare-CDN-Cache-Control`), `X-Accel-Expires` and `Edge-Control`. A proxy-specific cache header outside this list is not touched; keep such rules off the token route. Without it, tRPC lets the headers `responseMeta` returns replace or join the `no-store` the call set, so a caching rule there (such as `s-maxage` on public queries, or a CDN or proxy cache header) could put the token in a shared cache. Pass it to every tRPC handler you create that serves the token query; on nestjs-trpc 2.14.0 and later that is `TRPCModule.forRoot({ trpc: { responseMeta: authResponseMeta(yours) } })`. Before 2.14.0 nestjs-trpc has no `responseMeta`, so nothing inside tRPC can replace the `no-store`: keep cache-setting middleware off the base path, or serve the token from Nest with `SessionCookies.csrfToken`.
  - NestJS: `no-store` does not reach a cache inside the app. Keep the token route out of `CacheInterceptor`, any other response cache, and any interceptor or middleware that sets `Cache-Control` after the handler.
  - The token stays bound to the session or pre-session and the cookie is still required next to it, and an unsafe request from an origin outside the allowlist is refused on its `Origin` and `Sec-Fetch-Site` whatever the token, and whatever the app's CORS lets a page read, so reading it from a response grants nothing a cross-site page could use. Attack tests A100 and A101 pin that.

## 0.6.0

### Minor Changes

- [#93](https://github.com/noctcore/auth/pull/93) [`5ef423f`](https://github.com/noctcore/auth/commit/5ef423f29ac787f97ec06e60e4bbefb672907732) Thanks [@Shironex](https://github.com/Shironex)! - The NestJS and tRPC adapters now work with a desktop shell served from its own scheme (such as `app://desktop`).
  
  - The CSRF cookie (`__Host-csrf`), the pre-session cookie (`__Host-presession`) and the blank cookie that clears a refused session take the session cookie's `SameSite` for the request's `Origin`, instead of a fixed `Lax`. A cookie written next to a new session takes that session cookie's own value. With the default `session.cookie.sameSite` (`'lax'`) nothing changes. An app that sets it to `'strict'`, `'none'` or a function now gets the same answer on these cookies too.
  - New `csrf.crossSiteOrigins` option in both adapters: exact origins whose cross-site requests are accepted. A listed origin passes the `Origin` check, and its `Sec-Fetch-Site: cross-site` requests pass the fetch-metadata check. The double-submit token is still required. Matching is exact (scheme, host and port). At boot, an entry fails if it is a wildcard, `null`, has no host, or carries a path, query, fragment or user info. The list is empty by default, so behaviour is unchanged until you name an origin. Trust a listed origin as much as your own: see the threat model.
  - Core: `resolveSameSite(config, origin)` gives the session cookie's `SameSite` for an origin (used by every cookie that travels with it), `verifyFetchSite` takes optional `origin` and `crossSiteOrigins` inputs, and `assertExactOrigins(origins, option)` checks an origin allowlist at boot. Each adapter also refuses `SameSite=None` when its cookies are not Secure, even if the cookie config claims they are.

- [#98](https://github.com/noctcore/auth/pull/98) [`1ac8ef2`](https://github.com/noctcore/auth/commit/1ac8ef25814bfed484dd94cd45f55ee107407712) Thanks [@Shironex](https://github.com/Shironex)! - Email normalisation is now configurable with `email.normalize`. The default (`'standard'`) is unchanged and stores byte-identical spellings, so existing data keeps matching.
  
  - `'ascii'`: the same spelling as the default, but an address with a non-ASCII character is answered with the new public code `email_not_ascii` (sign-in still answers `invalid_credentials`, with `email_not_ascii` as the audited reason). The tRPC adapter maps it to `BAD_REQUEST`.
  - `'unicode'`: keeps Unicode addresses. NFC, then lowercase of the domain and the local part (the Greek final sigma folded to the plain one in the local part, so case variants of a Greek address stay one account; a domain keeps a typed final sigma, as IDNA2008 does). Refuses invisible, bidi, control, unassigned and compatibility characters, punycode labels, any part that mixes scripts (the Chinese, Japanese and Korean mixes with Latin are allowed), the dotless i, the IPA Extensions block (U+0250 to U+02AF) and a combining dot above on i or j. So a letter from another script, an invisible character, a compatibility form or one of those Latin letters cannot make a lookalike account. There is no UTS 39 confusables check: an address written wholly in another script, or with another same-script lookalike, is accepted as a different account, and the verification mail to that mailbox is the backstop.
  - A function `(email) => string | null`: your own policy. It must be pure, deterministic and idempotent, and return a single plain address (exactly one `@`, non-empty parts, no whitespace, commas, angle brackets or control characters, at most 254 bytes). `createAuth` runs it over a sample at startup and refuses one that throws, returns something unusable, answers differently twice, is not idempotent or merges different mailboxes; on each call an address whose result is unusable or not a fixed point is refused and logged with the error's class name only.
  
  One resolved normaliser now serves every flow (register, login, password reset, email verification, email change, invitations), every stored address and every counter key. It is exposed as `auth.normalizeEmail(email)` for your own code and as `normalizeEmail` and `parseEmail` on the plugin context; the exported `normalizeEmail` stays the `standard` policy. An unknown policy name fails at startup.
  
  Lookups by address are now exact on the core's side for every policy: a user row whose stored email is not exactly the normalised address asked for counts as not found, so a store behind a case- or accent-insensitive collation cannot reach one account under several spellings with separate lockout and rate-limit keys. `userStoreConformance` gains the case "different spellings must not match", and the plugin context gains `findCredentialByEmail`. A binary or accent-sensitive collation on the email column is recommended (see the auth-prisma README).
  
  Changing the policy on a live database needs a data migration first: rows stored under the old policy no longer match. The package does not migrate data; see the configuration reference.
  
  Upgrade note: because lookups are now exact, a row whose email was written outside the flows (an import, an admin tool, a seed) in a spelling the normaliser would not produce is unreachable, even under the default policy: its owner can no longer sign in, reset or be found by address. Before upgrading, find the rows where the stored email differs from `auth.normalizeEmail(email)` (for the default policy, any row with uppercase letters, surrounding whitespace or a non-ASCII character), then rewrite them or merge duplicates.

- [#96](https://github.com/noctcore/auth/pull/96) [`0713d60`](https://github.com/noctcore/auth/commit/0713d60d21052e2d24c9ddd23a59225ec5e5a80e) Thanks [@Shironex](https://github.com/Shironex)! - Add two opt-in lockout options, both off by default, so the default lockout (a capped temporary lock answered like a wrong password) is unchanged.
  
  - `throttle.lockout.permanent: { afterLocks, trustedDevices? }`: after `afterLocks` temporary locks in a row (a successful sign-in or a completed password reset resets the count), the next lock holds until an admin lifts it with the new `auth.lockout.clear({ email | userId, meta })`; `auth.lockout.inspect` reads the state. A password reset does not lift it. The lock is kept under the user id, so it follows the account through an email change; a lock on an address with no account is cleared when someone signs up on it. A permanent lock ends the account's sessions (`onSessionsRevoked` hears `locked-permanently`), writes an `account.locked_permanently` audit row, mails the owner a `lockout` mail with `permanent: true`, and runs the new `onPermanentLock` hook. With `trustedDevices` (the default) the owner's device cookie still gets through and no session may change the email; with `trustedDevices: false` every session and device cookie ends and every session door is refused until the clear, session validation included, so a session the background revocation failed to end is refused on its next request. Trade-off: anyone who knows an address can lock its owner out on purpose, so pair it with a captcha and per-IP rate limits.
  - `throttle.lockout.revealLocked`: login answers the new public code `account_locked` (with `retryAfterSeconds` for a temporary lock) instead of `invalid_credentials` while the address is locked. Trade-off: the answer tells anyone that the address is locked and when it lifts, an enumeration signal the generic answer does not give.
  
  `AuthErrorCode` gains `account_locked`; code that switches exhaustively over it needs a case. `@noctcore/auth-trpc` maps it to `FORBIDDEN`. The counter store conformance suite gains a case for the far-future expiry the permanent tier stores its marker with.

- [#100](https://github.com/noctcore/auth/pull/100) [`5144b55`](https://github.com/noctcore/auth/commit/5144b55b2e39d1dd82a71c3fdbfbaf184be45046) Thanks [@Shironex](https://github.com/Shironex)! - `sessions.list` no longer returns the session's store key. Each entry now carries a public `handle` in place of `id`: an HMAC-SHA-256 of the store key under a key derived from the server secret, as 43 characters of unpadded base64url, so a page that shows the list (or anything that reads it) never learns a store key, and a leaked store cannot be matched against handles without the secret. `sessions.revoke` takes `{ session, handle, meta }` and looks the handle up among the caller's own live sessions only; a handle it does not find (garbage, a raw store key, a gone session or another user's) answers `{ revoked: false }`, always the same. Another device still needs a fresh password proof, asked before any lookup.
  
  `onSessionsRevoked` now also receives `sessionHandles`, the same sessions' handles in the order of `sessionIds`, for every reason (`evicted` included), so apps can match revocations against the list. The new `auth.sessions.handle(sessionId)` (and `sessionHandle` on the plugin context) maps a store key you hold on the server to its handle. Rotating the server secret changes every handle; sessions survive it.
  
  `@noctcore/auth-trpc`: `sessionSummaryOutput` has `handle` in place of `id` and strips a store key a procedure returns, and `revokeSessionInput` is `{ handle }`.
  
  Migration (a breaking change to a public shape): rename `id` to `handle` in your session list and revoke routes and in any client code, and drop session ids a client stored, since revoke no longer accepts a store key: list again and use the handles it returns. See "Session handles" on the Sessions and expiry page.

- [#110](https://github.com/noctcore/auth/pull/110) [`7376b1e`](https://github.com/noctcore/auth/commit/7376b1e0b066238cb930d0ae248c1a08b0f41db3) Thanks [@Shironex](https://github.com/Shironex)! - `rateLimited` in the tRPC adapter can now count per signed-in user, take named tiers and skip exempt procedures. Counting per client IP stays the default.
  
  - A rule with `keyBy: 'user'` counts a signed-in caller by user, across IPs. The user comes only from the session the core accepted; a call with no session or with a refused cookie counts by its client IP. The counter key holds the core's keyed hash of the user id (an HMAC under a key derived from the server secret), never the id or a plain hash of it.
  - `createAuthMiddlewares(t, { rateLimits })` takes named rules, checked at boot. `rateLimited(name, 'tier')` picks one (tier names are typed, an unknown one throws); without a rule, `rateLimited(name)` takes the tier named `name`, then the `default` tier, then 10 a minute as before.
  - A procedure whose meta says `rateLimit: 'exempt'` is never counted, also by a limit on its base procedure. Add `RateLimitMeta` to your meta type. The nestjs-trpc `RateLimitMiddleware` reads the same meta and takes `keyBy`.
  - `TrpcAuth['context']` now needs `keyedHash(purpose, message)`. The object `createAuth` returns has it; a hand-made stand-in must add it.
  - New exported types: `AuthMiddlewareOptions`, `RateLimitKeyBy`, `RateLimitMeta`, `TrpcRateLimitRule`.

- [#94](https://github.com/noctcore/auth/pull/94) [`8ca8e82`](https://github.com/noctcore/auth/commit/8ca8e82e4e136d31ccd46048541921ba567fc7bc) Thanks [@Shironex](https://github.com/Shironex)! - Trust proxies by address, and read the client IP from an edge header through a trusted hop.
  
  - `trustedHops` (in `clientIp` and in both adapters) also takes a list of proxy addresses, CIDR ranges and the Express presets `loopback`, `linklocal` and `uniquelocal`, which expand to the same ranges Express uses. With a list, `X-Forwarded-For` is read only when the socket address is inside it, and the first address outside it, from the right, is the client. `resolveTrustedProxies` checks and expands a list and refuses an unknown name, a malformed range or a range that holds every address (such as `0.0.0.0/0`); on the request path such a list trusts nothing instead of throwing. An IPv6 zone id on the socket address is dropped before matching. `isTrustedAddress`, `resolveTrustedHops`, `resolveClientIpHeader`, `TRUST_PROXY_PRESETS` and the `TrustedHops` type are exported too.
  - New opt-in `clientIpHeader` option in the NestJS and tRPC adapters (and `trustedHeader` in `clientIp`), such as `cf-connecting-ip`. It needs `trustedHops` as a proxy list naming the edge (it is refused at boot with a hop count, which never checks the socket address), and the header wins only when the socket address is inside that list and the value is exactly one valid IP; otherwise the `X-Forwarded-For` rule decides. Off by default, so nothing changes until it is set.
  - `trustedHopsFromEnv` and `configureTrustProxy` accept a `TRUST_PROXY` list such as `loopback, 10.0.0.0/8` and return it with the presets expanded (their return type is now `TrustedHops`, a number or a list); `configureTrustProxy` sets the same list on Express.

- [#64](https://github.com/noctcore/auth/pull/64) [`2ab09b7`](https://github.com/noctcore/auth/commit/2ab09b7b3769e14fbd72259138592df55a8bb3bb) Thanks [@Shironex](https://github.com/Shironex)! - Add the membership plugin, `@noctcore/auth/membership`, with flows under `auth.membership` (`add`, `changeRole`, `remove`): nobody acts on themselves (`self_target`, by user id), the last member holding an admin role in a scope can be neither demoted nor removed (`last_admin`, decided atomically by the store), the actor's right is read from the store on every call (`canManage`, default: the actor holds an admin role), and every flow first reads the acting session live from the store.   - New public error codes `self_target` and `last_admin`. `AUTH_ERROR_TRPC_CODES` in `@noctcore/auth-trpc` maps them to `FORBIDDEN` and `CONFLICT`. Code that switches over every `AuthErrorCode` with a `never` check needs cases for them.

- [#69](https://github.com/noctcore/auth/pull/69) [`5fde7f8`](https://github.com/noctcore/auth/commit/5fde7f814608d51aab840dc57647ed2c77bbb5bd) Thanks [@Shironex](https://github.com/Shironex)! - Only one procedure per HTTP request can write cookies. Send session-writing mutations one per request, with `httpLink` (through `splitLink`, as the docs show). Procedures without the marker share a batch as before.

## 0.3.0

### Minor Changes

- [#54](https://github.com/noctcore/auth/pull/54) [`8544dd8`](https://github.com/noctcore/auth/commit/8544dd802138668f127a19d2967878767fc3388b) Thanks [@Shironex](https://github.com/Shironex)! - Add `@noctcore/auth-trpc`, the tRPC adapter. `createAuthContext` checks its options at boot and builds `ctx.auth` once per request on the fetch or Node adapters: the session validated through the core, the request meta with the client IP through the trusted hops (at most 16), and `setSession`, `signOut` and `clearSession`, which write the cookies with a CSRF token bound to the new session or pre-session. `createAuthMiddlewares(t)` returns `publicProcedure` and `protectedProcedure` plus `csrf`, `authed`, `freshAuth`, `role`, `rateLimited` and `writesCookies`, the only way to the cookie writers (`setSession`, `signOut` and `clearSession` are on `ctx.auth` only after it, typed as `AuthWriter`, and refuse at run time anywhere else), which also refuses a streamed batch (detected as tRPC does, from `trpc-accept` or `Accept`) and a subscription before the flow runs; every session check also runs the CSRF check on mutations, and `rateLimited` refuses when the counter store is down. `toTRPCError` maps every `AuthErrorCode` from the public code only (an unknown code becomes `internal`), and `authErrorFormatter` never sends a stack, answers input errors with paths and issue codes, a body that does not parse and the codes `PARSE_ERROR`, `METHOD_NOT_SUPPORTED`, `UNSUPPORTED_MEDIA_TYPE`, `PAYLOAD_TOO_LARGE` and `NOT_FOUND` with a fixed message, and internal errors with `internal`. Zod 4 input and output schemas for every auth flow, with outputs that strip unknown keys. `assertProceduresGuarded` and `assertNoSecretQueries` fail on an unguarded procedure and on a query that carries a secret. For nestjs-trpc, `AuthGuardMiddleware` is closed unless a procedure's meta says `auth: 'public'`, with `WritesCookiesMiddleware`, `RoleMiddleware`, `FreshAuthMiddleware` and `RateLimitMiddleware` running the same bodies. Peers: `@trpc/server` 11.22.1 or later within 11, and `zod` 4.3 or later within 4.
