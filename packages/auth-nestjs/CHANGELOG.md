## 0.8.0

### Minor Changes

- [#190](https://github.com/noctcore/auth/pull/190) [`72a2d67`](https://github.com/noctcore/auth/commit/72a2d671ebb6e0b9a75b6c64280a050de377393a) Thanks [@Shironex](https://github.com/Shironex)! - The CSRF options are now checked for their type at startup, in `resolveCsrfSettings` and so in both adapters (`AuthModule.forRoot` and `createAuthContext`), with an `AuthConfigError` naming the option. `csrf.allowSameSite` must be `true` or `false` (or left out): it was read by truthiness, so the string `"false"` from the environment turned the weaker same-site mode on. `csrf.secrets` must be a list of strings or bytes, `csrf.allowedOrigins` and `csrf.crossSiteOrigins` lists of strings, and `csrf.headerName` a string. In the NestJS adapter, `csrf.exempt` must be a list of paths and RegExps.
  
  **Behaviour change:** a configuration that started before can now refuse to start. `allowSameSite` given as a string or a number (it ran in same-site mode for any truthy value, `"false"` included), `allowedOrigins` given as one string (it was read character by character, so every unsafe request was refused), and an `exempt` given as one string (read character by character, it exempted the path `/` from CSRF), or holding an entry that is neither a string nor a RegExp (the first unsafe request then threw), are refused at boot. Pass real booleans and lists, for example `allowSameSite: process.env.CSRF_ALLOW_SAME_SITE === 'true'`.

- [#189](https://github.com/noctcore/auth/pull/189) [`3f1c849`](https://github.com/noctcore/auth/commit/3f1c849e570ec2dda7eecbea01aff45c273621f6) Thanks [@Shironex](https://github.com/Shironex)! - During a CSRF secret rollover (`csrf.secrets: [NEW, OLD]`) a safe request now replaces a token signed by the previous secret with one under the current secret, in `handOutCsrfToken` and so in both adapters. Before, any token that verified under any listed secret was kept, so no client moved to the new secret while the old one was listed: removing the old secret answered every client's next unsafe request with a 403, and a leaked old secret could not be retired early. The old secret can go once clients have made a safe request since the rollover; the NestJS guide and the CSRF learn page say so. The unsafe-request check is unchanged: the header must equal the cookie.
  
  **Behaviour change:** during a rotation, a page that kept the old token in memory (a single page app or desktop shell that read `csrfToken()` once, or a second tab) gets one 403 after another request reissued the cookie, because its header no longer equals the cookie. It should read the token again from the cookie or the token route, or retry once after a safe request. Before, such a page kept working until the old secret was removed, and then failed the same way.

- [#179](https://github.com/noctcore/auth/pull/179) [`941aa2a`](https://github.com/noctcore/auth/commit/941aa2a8e6666559abdba82183eed3756d0004fd) Thanks [@Shironex](https://github.com/Shironex)! - `describeRoutes` and the startup contradiction check now include the handlers a controller inherits from a base class or a mixin. They used to read only the controller's own prototype, so an inherited route (public ones included) was missing from the route list, and an inherited handler marked both `@Public()` and `@RequireRole()` (or `@RequireFreshAuth()`) was never checked. The chain is walked the way Nest's `MetadataScanner` finds routes: each method name is taken once at the nearest level, so an override in the subclass replaces the base handler, and an override without a route decorator is no route. The guard already failed closed at request time, so no route was open.
  
  Behaviour change: an app whose controller inherits a handler that is `@Public()` and also requires a role or fresh auth (on the handler, or through a `@Public()` on the subclass) no longer starts, and `AuthModule` throws `AuthConfigError` naming the route. So does an inherited `@RequireRole()` without the `roles` option. Remove one of the contradicting decorators.

- [#193](https://github.com/noctcore/auth/pull/193) [`7f7f3a3`](https://github.com/noctcore/auth/commit/7f7f3a39282668a11a5b6bd28b96ed1abaa2025e) Thanks [@Shironex](https://github.com/Shironex)! - The startup option checks are finished: the value options listed below, which were read without a type check, now refuse a value of the wrong type when `createAuth`, a plugin, a factory (`argon2id`, `turnstile`, `pwnedPasswords`) or an adapter starts, with an `AuthConfigError` that names the option, instead of a raw `TypeError` at startup or a crash on the first request that reads it.
  
  The ports (`logger`, `clock`, `metrics`, and the `logger` of `turnstile` and `pwnedPasswords`) are not checked.
  
  - `throttle: { lockout: null }` boots with the defaults, like a missing `lockout` (it threw a `TypeError`).
  - A duration that does not parse (`'15 min'`, `NaN`, a negative number) throws an `AuthConfigError` naming the key instead of a `TypeError` from the parser: the flow `ttl`s, `passwordReset.ticketTtl`, `emailChange.revertTtl` and `blockAfterRevert`, the `session` durations, the `throttle.lockout` durations and rule windows, `background.timeout`, and the plugins' durations and rule windows.
  - A missing `csrf`, `csrf.secrets` or `csrf.allowedOrigins` in either adapter throws an `AuthConfigError` naming it instead of a `TypeError`.
  - A `session.idleTimeout: null` now gives the default on every sign-in; it passed the startup check and then threw on each sign-in.
  - A `null` `twoFactor` `required`, `enforcement` or `importedRecoveryCodes`, a `null` `previousSecret`, `background`, `background.maxPending`, `clientIpHeader` and `argon2id(null)` or `pwnedPasswords(null)` count as left out.
  
  **Behaviour change:** a configuration that started before can now refuse to start. Each value refused was already broken (it crashed on first use, turned a check off, or quietly meant something else), but a deployment that passes one stops booting until it is fixed. Now refused:
  
  - a list with an empty slot (`[, '/webhook']`, a hole in `csrf.secrets`, `csrf.allowedOrigins`, `csrf.crossSiteOrigins`, `csrf.exempt`, `previousSecret`, `plugins` or membership `adminRoles`): the checks walked the list with `.some` or `.every`, which skip a hole, and later code read it as `undefined`;
  - an `emailVerification.kind`, `passwordReset.kind` or `emailChange.kind` other than `'code'` or `'link'` (a typo such as `'Link'` ran the other kind);
  - a `urls` entry, `passwordReset.enqueue`, `background.waitUntil`, a plugin's `flows`, membership `canManage`, twoFactor `required`, or an adapter's `roles` that is not a function (each threw on the first request that called it);
  - a `password.breachCheck` that is neither a function nor `false`, and a `captcha` without a `verify` function (the string `"false"` counted as configured, and the first sign-up or login threw);
  - a `secret` that is neither a string nor bytes, a `session.cookie.name` that is not a string, a `session.attributes` without `parse`, and a fixed `session.cookie.sameSite` other than `'lax'`, `'strict'` or `'none'` (`'None'` skipped the check that refuses `None` without Secure; a function's value is checked the same way when a cookie is built);
  - a `plugins` that is not a list of plugins with an `id`, or a plugin `requires` that is not a list;
  - a `throttle.lockout` rule that is not an object (it fell back to the default silently);
  - in `argon2id()`, an `unsafeAllowWeakParameters` that is not `true` or `false`, a cost parameter that is not a whole number of at least 1, and a `secret` that is not bytes;
  - in `turnstile()`, a missing or empty `secret`, a `checkAction` that is not `true` or `false` (read by truthiness), an `expectedHostnames` given as one string (matched as a substring, so any part of the host name passed), a `timeoutMs` that is not a number above zero, and a `fetch` or `onResult` that is not a function; in `pwnedPasswords()` the same for `timeoutMs`, `fetch` and `onResult`, and a `userAgent` or `baseUrl` that is not a string;
  - a `clientIpHeader` that is not a string (it was coerced with `String`);
  - in `createAuthMiddlewares(t, { rateLimits })` and `rateLimited(name, rule)`, a rule that is not an object, a `limit` that is not a whole number of at least 1 (a `NaN` or zero limit refused every call), and a `window` that is not a duration longer than zero.
  
  To fix a refused value, convert it first, for example `process.env.CHECK_ACTION === 'true'`, `Number(process.env.LIMIT ?? 10)`, or a list built with `.split(',')`.

- [#134](https://github.com/noctcore/auth/pull/134) [`eb87941`](https://github.com/noctcore/auth/commit/eb8794111d0d893fa4473aa0703a978b4af15059) Thanks [@Shironex](https://github.com/Shironex)! - Both adapters can now validate a request without counting it as activity, so a page that polls on a timer no longer keeps an idle session alive for its whole absolute lifetime. The default is unchanged: every request touches.
  
  - NestJS: a new `touch` option on `AuthModule`, `true`, `false` or a predicate `(request) => boolean` over the request's method, path (a global prefix included, no query string) and headers. It runs before the one validation of the request. A request it marks passive is answered with its session and leaves `lastActiveAt` alone. New exported type `TouchRequest`.
  - tRPC: a new `touch` option on `createAuthContext`, `true`, `false` or a predicate `(path) => boolean` asked about each procedure path of the request, and a procedure meta `touch: false` (on `AuthProcedureMeta`). Both are read from the calls tRPC parsed before it built the context. A batch touches when any of its procedures is active, and a request whose adapter names no calls touches as before.
  - The CSRF checks and the guards' decisions do not change with the option, and the session is still validated once per request.

- [#135](https://github.com/noctcore/auth/pull/135) [`f4f0852`](https://github.com/noctcore/auth/commit/f4f085256879f203a3ebb998695de571d7cf57ab) Thanks [@Shironex](https://github.com/Shironex)! - Both adapters now hand the CSRF token to a client that cannot read the API's cookies, such as a desktop shell on its own scheme or a web app on another origin than the API. Until now such a client had no token for its first sign-in, nor for any unsafe request after a restart with a persistent session.
  
  - NestJS: `SessionCookies.csrfToken(request, response)` returns `{ csrfToken }` for a `@Public()` GET route (for example `GET /csrf-token`). It is exactly the token `CsrfMiddleware` set or kept as the `csrf` cookie on that response, minting the pre-session and the cookie when missing, and it marks the response `Cache-Control: no-store`. It throws an `AuthConfigError` on an exempt path (which still mints nothing) and on an unsafe method.
  - tRPC: `ctx.auth.csrfToken()` returns `{ csrfToken }` in a public query sent with GET, with the same guarantees. It throws an `AuthConfigError` on a request with an unsafe method, on a streamed batch (`httpBatchStreamLink`) and in a subscription.
  - tRPC: `authResponseMeta(responseMeta)` wraps the app's `responseMeta` (or stands alone as `authResponseMeta()`) and keeps `Cache-Control: no-store` on every response that handed out a token, dropping these headers the app returned: `Cache-Control`, `Surrogate-Control`, `CDN-Cache-Control`, every `*-CDN-Cache-Control` (such as `Cloudflare-CDN-Cache-Control`), `X-Accel-Expires` and `Edge-Control`. A proxy-specific cache header outside this list is not touched; keep such rules off the token route. Without it, tRPC lets the headers `responseMeta` returns replace or join the `no-store` the call set, so a caching rule there (such as `s-maxage` on public queries, or a CDN or proxy cache header) could put the token in a shared cache. Pass it to every tRPC handler you create that serves the token query; on nestjs-trpc 2.14.0 and later that is `TRPCModule.forRoot({ trpc: { responseMeta: authResponseMeta(yours) } })`. Before 2.14.0 nestjs-trpc has no `responseMeta`, so nothing inside tRPC can replace the `no-store`: keep cache-setting middleware off the base path, or serve the token from Nest with `SessionCookies.csrfToken`.
  - NestJS: `no-store` does not reach a cache inside the app. Keep the token route out of `CacheInterceptor`, any other response cache, and any interceptor or middleware that sets `Cache-Control` after the handler.
  - The token stays bound to the session or pre-session and the cookie is still required next to it, and an unsafe request from an origin outside the allowlist is refused on its `Origin` and `Sec-Fetch-Site` whatever the token, and whatever the app's CORS lets a page read, so reading it from a response grants nothing a cross-site page could use. Attack tests A100 and A101 pin that.

- [#93](https://github.com/noctcore/auth/pull/93) [`5ef423f`](https://github.com/noctcore/auth/commit/5ef423f29ac787f97ec06e60e4bbefb672907732) Thanks [@Shironex](https://github.com/Shironex)! - The NestJS and tRPC adapters now work with a desktop shell served from its own scheme (such as `app://desktop`).
  
  - The CSRF cookie (`__Host-csrf`), the pre-session cookie (`__Host-presession`) and the blank cookie that clears a refused session take the session cookie's `SameSite` for the request's `Origin`, instead of a fixed `Lax`. A cookie written next to a new session takes that session cookie's own value. With the default `session.cookie.sameSite` (`'lax'`) nothing changes. An app that sets it to `'strict'`, `'none'` or a function now gets the same answer on these cookies too.
  - New `csrf.crossSiteOrigins` option in both adapters: exact origins whose cross-site requests are accepted. A listed origin passes the `Origin` check, and its `Sec-Fetch-Site: cross-site` requests pass the fetch-metadata check. The double-submit token is still required. Matching is exact (scheme, host and port). At boot, an entry fails if it is a wildcard, `null`, has no host, or carries a path, query, fragment or user info. The list is empty by default, so behaviour is unchanged until you name an origin. Trust a listed origin as much as your own: see the threat model.
  - Core: `resolveSameSite(config, origin)` gives the session cookie's `SameSite` for an origin (used by every cookie that travels with it), `verifyFetchSite` takes optional `origin` and `crossSiteOrigins` inputs, and `assertExactOrigins(origins, option)` checks an origin allowlist at boot. Each adapter also refuses `SameSite=None` when its cookies are not Secure, even if the cookie config claims they are.

- [#94](https://github.com/noctcore/auth/pull/94) [`8ca8e82`](https://github.com/noctcore/auth/commit/8ca8e82e4e136d31ccd46048541921ba567fc7bc) Thanks [@Shironex](https://github.com/Shironex)! - Trust proxies by address, and read the client IP from an edge header through a trusted hop.
  
  - `trustedHops` (in `clientIp` and in both adapters) also takes a list of proxy addresses, CIDR ranges and the Express presets `loopback`, `linklocal` and `uniquelocal`, which expand to the same ranges Express uses. With a list, `X-Forwarded-For` is read only when the socket address is inside it, and the first address outside it, from the right, is the client. `resolveTrustedProxies` checks and expands a list and refuses an unknown name, a malformed range or a range that holds every address (such as `0.0.0.0/0`); on the request path such a list trusts nothing instead of throwing. An IPv6 zone id on the socket address is dropped before matching. `isTrustedAddress`, `resolveTrustedHops`, `resolveClientIpHeader`, `TRUST_PROXY_PRESETS` and the `TrustedHops` type are exported too.
  - New opt-in `clientIpHeader` option in the NestJS and tRPC adapters (and `trustedHeader` in `clientIp`), such as `cf-connecting-ip`. It needs `trustedHops` as a proxy list naming the edge (it is refused at boot with a hop count, which never checks the socket address), and the header wins only when the socket address is inside that list and the value is exactly one valid IP; otherwise the `X-Forwarded-For` rule decides. Off by default, so nothing changes until it is set.
  - `trustedHopsFromEnv` and `configureTrustProxy` accept a `TRUST_PROXY` list such as `loopback, 10.0.0.0/8` and return it with the presets expanded (their return type is now `TrustedHops`, a number or a list); `configureTrustProxy` sets the same list on Express.

- [#67](https://github.com/noctcore/auth/pull/67) [`fb9f5d8`](https://github.com/noctcore/auth/commit/fb9f5d80dcdc515ff0e09b453c18136adddbd6ca) Thanks [@Shironex](https://github.com/Shironex)! - Background work (every mail, lock notices, and a password reset job run without `passwordReset.enqueue`) now goes through one runner, configured with the new optional `background` option of `createAuth`:
  
  - `background.waitUntil(promise)` receives each task's promise as the task starts, so runtimes that freeze the instance after the response (Vercel, Cloudflare Workers) can keep mail sends alive. The promise never rejects.
  - `auth.flush()` resolves once no background task is left that has neither settled nor timed out, tasks started while it waits included. Await it on graceful shutdown of a long-lived process, before closing your connections. Pass `{ timeout }` to give up after that long; whatever is still running is logged as `Background flush stopped waiting` and left running. `AuthModule` from `@noctcore/auth-nestjs` now does this in `beforeApplicationShutdown`, bounded by its new `shutdownTimeout` option (default `'10s'`), so a mailer that never settles cannot hang `app.close()` or SIGTERM.
  - `background.timeout` stops waiting on a task that runs past it, so `flush` and `waitUntil` no longer wait for it. The task is logged as `Background task timed out: <label>`. A promise cannot be cancelled, so the task keeps running.
  - `background.maxPending` refuses to start a new task while that many are still running, timed out or not. The dropped task is logged as `Background task dropped: <label>`, with the user id when there is one. This bounds memory when a mailer hangs instead of failing.
  
  Timeouts and drops are counted on `metrics` as `auth_background_task` (exported as `BACKGROUND_METRIC`), with `task` and `outcome` labels. All three options are off by default, and behaviour without them is unchanged. One small exception: a detached reset job that throws is now logged as `Background task failed: password reset job` instead of `Detached password reset job failed`.
  
  Task labels, as they appear in these logs and in the `task` label of the metric:
  
  - `mail <type>` (such as `mail lockout` or `mail password-reset`): one per mail, capped.
  - `verification mail`: a sign-up's verification code and mail, capped.
  - `audit <type>`: the `register.created` and `account.locked` rows, uncapped.
  - `existing address notice`: the owner lookup and the `register.existing` row of a sign-up with a taken address, uncapped; its mail is a `mail account-exists` task.
  - `password reset job`: a reset job run without `enqueue`, uncapped; its mail is a `mail password-reset` or `mail password-reset-code` task.
  
  The `lockout notice` label is gone: a lock notice is now an `audit account.locked` task plus a `mail lockout` task, so the mail no longer waits for the audit write, and a failure that was logged as `Background task failed: lockout notice` is now logged under one of those two labels (a failed send still as `Mailer failed`). Update any alert that matches the old label. A reset job run by your queue worker through `auth.jobs.processPasswordReset` hands the mail to the mailer and returns, as before. Drops, timeouts and failures go to the configured `logger`, which is silent by default.
  
  Under `maxPending` only mail is dropped, plus the `email.verification_sent` row of a dropped verification mail (a dropped mail was not sent). Every other audit row written off the response path (`register.created`, `register.existing`, `account.locked`, `password.reset_request_ignored`) is in a task the cap never drops and never counts. Those tasks take no slots, so a hung audit sink, or a user store that hangs during the lookup of a taken-address sign-up or a detached reset job, still grows memory as before.
