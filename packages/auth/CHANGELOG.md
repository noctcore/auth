# @noctcore/auth

## 0.5.0

### Minor Changes

- [#67](https://github.com/noctcore/auth/pull/67) [`fb9f5d8`](https://github.com/noctcore/auth/commit/fb9f5d80dcdc515ff0e09b453c18136adddbd6ca) Thanks [@Shironex](https://github.com/Shironex)! - Background work (every mail, lock notices, and a password reset job run without `passwordReset.enqueue`) now goes through one runner, configured with the new optional `background` option of `createAuth`:
  
  - `background.waitUntil(promise)` receives each task's promise as the task starts, so runtimes that freeze the instance after the response (Vercel, Cloudflare Workers) can keep mail sends alive. The promise never rejects.
  - `auth.flush()` resolves once no background task is left that has neither settled nor timed out, tasks started while it waits included. Await it on graceful shutdown of a long-lived process, before closing your connections. Pass `{ timeout }` to give up after that long; whatever is still running is logged as `Background flush stopped waiting` and left running. `AuthModule` from `@noctcore/auth-nestjs` now does this in `beforeApplicationShutdown`, bounded by its new `shutdownTimeout` option (default `'10s'`), so a mailer that never settles cannot hang `app.close()` or SIGTERM.
  - `background.timeout` stops waiting on a task that runs past it, so `flush` and `waitUntil` no longer wait for it. The task is logged as `Background task timed out: <label>`. A promise cannot be cancelled, so the task keeps running.
  - `background.maxPending` refuses to start a new task while that many are still running, timed out or not. The dropped task is logged as `Background task dropped: <label>`, with the user id when there is one. This bounds memory when a mailer hangs instead of failing.
  
  Timeouts and drops are counted on `metrics` as `auth_background_task` (exported as `BACKGROUND_METRIC`), with `task` and `outcome` labels. All three options are off by default, and behaviour without them is unchanged. One small exception: a detached reset job that throws is now logged as `Background task failed: password reset job` instead of `Detached password reset job failed`.
  
  Task labels, as they appear in these logs and in the `task` label of the metric:
  
  - `mail <type>` (such as `mail lockout` or `mail password-reset`): one per mail, capped.
  - `verification mail`: a sign-up's verification code and mail, capped.
  - `audit <type>`: the `register.created` and `account.locked` rows, uncapped.
  - `existing address notice`: the owner lookup and the `register.existing` row of a sign-up with a taken address, uncapped; its mail is a `mail account-exists` task.
  - `password reset job`: a reset job run without `enqueue`, uncapped; its mail is a `mail password-reset` or `mail password-reset-code` task.
  
  The `lockout notice` label is gone: a lock notice is now an `audit account.locked` task plus a `mail lockout` task, so the mail no longer waits for the audit write, and a failure that was logged as `Background task failed: lockout notice` is now logged under one of those two labels (a failed send still as `Mailer failed`). Update any alert that matches the old label. A reset job run by your queue worker through `auth.jobs.processPasswordReset` hands the mail to the mailer and returns, as before. Drops, timeouts and failures go to the configured `logger`, which is silent by default.
  
  Under `maxPending` only mail is dropped, plus the `email.verification_sent` row of a dropped verification mail (a dropped mail was not sent). Every other audit row written off the response path (`register.created`, `register.existing`, `account.locked`, `password.reset_request_ignored`) is in a task the cap never drops and never counts. Those tasks take no slots, so a hung audit sink, or a user store that hangs during the lookup of a taken-address sign-up or a detached reset job, still grows memory as before.

- [#63](https://github.com/noctcore/auth/pull/63) [`76717de`](https://github.com/noctcore/auth/commit/76717de578fbd4f83973dcf544acafeb1d5c9dad) Thanks [@Shironex](https://github.com/Shironex)! - Add email change with a revert link: `requestEmailChange`, `confirmEmailChangeCode`, `confirmEmailChangeLink` and `revertEmailChange`.
  
  - A request needs a live session with a credential proof inside `session.freshAuthAge`, then runs the new `beforeEmailChange` hooks. The two-factor plugin uses that hook: with a confirmed factor, the request needs a step-up held by the session or a code in `secondFactor`.
  - An 8-digit code (or, with `emailChange.kind: 'link'` and `urls.confirmEmailChange`, a link) goes to the new address. A taken address, or one held for another account, gets the same answer after the same store calls, and its owner gets an `email-change-in-use` mail instead. A confirm needs a live session of the same account. A pending change dies on a password change or reset and on signing out of other devices or everywhere.
  - A confirmed change voids reset and verification tokens and writes the revert link before it moves the address in one compare-and-set, marks it verified, revokes every session (re-issuing the caller's with the new re-issue via `email-changed`), and mails the old address `email-changed` with a revert link valid for `emailChange.revertTtl` (7 days, the minimum). While that link lives, the old address is held for the account: sign-up on it answers as for a taken address, and so do other accounts' changes to it.
  - A revert restores the old address and removes the password in one write, revokes every session, voids reset, verification and change tokens, keeps second factors (an owner who cannot pass one an intruder enrolled needs support), blocks the lost address for this account for `emailChange.blockAfterRevert` (30 days), and writes `email.change_reverted` with `review: true`. If the old address has an account anyway, it removes the password and sessions, answers `email_in_use`, and locks the account out: no session is issued for it, reset requests send nothing and reset links are refused, until the owner's link (kept alive as long) finishes or support calls the new `auth.clearEmailRevertLockout`, which also voids the revert link and the hold; it never lapses on its own. A revert link refuses once the account no longer names the address the change moved it to. New `auth.isAddressHeld(email)` for an app's own user-creating paths. No new change starts while a revert link lives, and password changes and resets do not void it.
  - New optional `UserStore.changeEmail`, returning `'changed' | 'taken' | 'stale'`, with conformance cases in `userStoreConformance` and an implementation in `MemoryUserStore` and `PrismaUserStore`. The flows need it and `urls.revertEmailChange`, and throw `AuthConfigError` without them. No schema change.
  - New mail events `email-change-confirm`, `email-change-in-use`, `email-changed` and `email-change-reverted`, and new `email.change_*` audit event types. A mailer or audit sink that switches over every type with a `never` check needs cases for them.
  - New doors `email-change-request`, `email-change-address`, `email-change` and `email-change-revert`; new revocation reasons `email-changed` and `email-reverted`; `OneTimeTokens.findLive`, `putKeyed`, `findKeyed` and `extendLink`; the `email.revert_lockout_cleared` audit event type.
  - `resetPassword` now checks the new password against the policy, then runs `beforePasswordReset`, and only then hashes, so a hook's refusal costs no hash. `AuthCore.checkNewPassword` and `hashCheckedPassword` split `hashNewPassword` for flows that run hooks between the two.

- [#70](https://github.com/noctcore/auth/pull/70) [`5b79f16`](https://github.com/noctcore/auth/commit/5b79f16f9a597db92131f6684114c9f872cac4f5) Thanks [@Shironex](https://github.com/Shironex)! - Every door that needs fresh authentication now reads it from the live session in the store, not from the session object the caller passes: revoking another device (`sessions.revoke`), starting and confirming a second-factor enrollment, and the two-factor `requireStepUp` check. `sessions.revokeOthers` already did this. A hand-built or copied session object claiming a recent `authenticatedAt` is refused with `fresh_auth_required`.
  
  Plugins get the same check as `context.requireFreshLiveSession(session)`. It answers `session_expired` unless the session is live and still the same user's, then `fresh_auth_required` as `requireFreshAuth` does, and returns the live copy.
  
  Behaviour change: at these doors, a session that has expired, gone idle, been revoked or been rotated away now gets `session_expired` instead of being judged on the object passed in. For example, `requireStepUp` on a session replaced by `reauthenticate` used to pass on the old object's proof.

- [#71](https://github.com/noctcore/auth/pull/71) [`c09f611`](https://github.com/noctcore/auth/commit/c09f611bc86253f33220e6d6ace54743de5cc1af) Thanks [@Shironex](https://github.com/Shironex)! - Add the invitations plugin, `@noctcore/auth/invitations`, with flows under `auth.invitations` (`create`, `list`, `revoke`, `accept`, `register`). Tokens are 256 random bits, stored only as a keyed hash, single use (spent atomically by the store), bound to the invited address and expiring after 7 days by default (at most 30). `accept` needs a session whose verified address is the invited one and issues no session; `register` creates an account only for an address that has none, marks it verified and issues its session through `issueSession` with `via: 'invitation'`, so the two-factor plugin still applies. The plugin refuses to start without `authorize`, asks it on every create, list and revoke and again for the inviter on accept, deletes an inviter's pending invitations when all their sessions are revoked, keeps one live invitation per scope and address, and limits creates per address, per inviter and per IP. `create` never reads the invited address from the user store.
  
  - New store port `InvitationStore`, with `invitationStoreConformance` and `MemoryInvitationStore` in `@noctcore/auth/testing`.
  - New mail event `invitation`, the first without a `userId`. A mailer that switches over every type with a `never` check needs a case for it.
  - New audit event types `invitation.created`, `invitation.deduplicated`, `invitation.revoked`, `invitation.accepted` and `invitation.refused`. An audit sink that switches over every type with a `never` check needs cases for them.
  - `revokeAllSessions` on the plugin context takes an optional `{ scope }`, passed to `onSessionsRevoked` as `scope`; the membership plugin names the scope of the change. Revoking every session deletes the inviter's invitations, only in that scope when one is named and in every scope otherwise; `two-factor-enabled` keeps them, like `revoke-others`.

- [#64](https://github.com/noctcore/auth/pull/64) [`2ab09b7`](https://github.com/noctcore/auth/commit/2ab09b7b3769e14fbd72259138592df55a8bb3bb) Thanks [@Shironex](https://github.com/Shironex)! - Add the membership plugin, `@noctcore/auth/membership`, with flows under `auth.membership` (`add`, `changeRole`, `remove`): nobody acts on themselves (`self_target`, by user id), the last member holding an admin role in a scope can be neither demoted nor removed (`last_admin`, decided atomically by the store), the actor's right is read from the store on every call (`canManage`, default: the actor holds an admin role), and every flow first reads the acting session live from the store. Session revocation is opt-in (`revokeSessionsOnChange`, default false) for apps that copy roles into sessions: then an attempted role change to another role, or a removal, revokes every session of the member through the epoch fence (revocation reason `membership-changed`), before and after the write, so an attempt the store refuses (`last_admin`, a stale or missing target) has still revoked them, while adding a member and setting the role a member already holds never revoke. The guards fail closed. The plugin does not scope data.
  
  - New store port `MembershipStore`, with `membershipStoreConformance` and `MemoryMembershipStore` in `@noctcore/auth/testing`.
  - New public error codes `self_target` and `last_admin`. `AUTH_ERROR_TRPC_CODES` in `@noctcore/auth-trpc` maps them to `FORBIDDEN` and `CONFLICT`. Code that switches over every `AuthErrorCode` with a `never` check needs cases for them.
  - New audit event types `membership.added`, `membership.role_changed`, `membership.removed` and `membership.refused`. An audit sink that switches over every type with a `never` check needs cases for them.
  - `SessionAccess` (the plugin context's `sessions`) gains `findActive(id)`, a read of a live session by id, so a plugin can check that the session it was handed is still live. It cannot mint or re-issue anything.

- [#65](https://github.com/noctcore/auth/pull/65) [`e73f7a0`](https://github.com/noctcore/auth/commit/e73f7a0096808eb2fa9f705fe6c32983fb752e08) Thanks [@Shironex](https://github.com/Shironex)! - Sign-up no longer waits on the work that differs between a taken and a new address. The answer waits on the door limit, the password hash and one insert; after that, a taken address's owner lookup, `account-exists` mail and `register.existing` audit event, and a new address's `register.created` audit event, verification token and `verify-email` mail, run in the background. On Postgres and Redis the taken path used to answer a few milliseconds slower, enough for `bun run bench:timing:stores` to tell the paths apart.
  
  On PostgreSQL and CockroachDB, the Prisma user store inserts through `createManyAndReturn` with `skipDuplicates`, so a taken address is a skipped insert instead of a failed statement. On PostgreSQL through `@prisma/adapter-pg`, a failed statement made the next query about 3 ms slower. Everywhere else the store keeps the old insert, where a unique violation answers `null`: on delegates without `createManyAndReturn` (MySQL, SQL Server), and where Prisma refuses the bulk insert with a validation error (SQLite, which has no `skipDuplicates`, and a `createData` or `select` with nested writes or relations). The store falls back on the first refusal and remembers it, so no existing setup breaks.
  
  Behaviour change: `auth.register` resolves before the verification mail is handed to the mailer and before the sign-up audit event is written. A test that reads the mail or the audit trail right after sign-up has to wait for them. A token store that fails while sign-up writes the verification code, or a user store that fails on the owner lookup, no longer fails the request. The error is logged as `Background task failed: verification mail` or `Background task failed: existing address notice`, and the user can ask for another verification mail.

### Patch Changes

- [#62](https://github.com/noctcore/auth/pull/62) [`57440a0`](https://github.com/noctcore/auth/commit/57440a046b8f63cbca56f273ac611a8d6d391ebb) Thanks [@Shironex](https://github.com/Shironex)! - The lockout backoff now rises one step per lock, not one step per request that crosses the limit. A large parallel burst could cross the account-wide limit several times before the lock was visible, and each crossing raised the tier, so the next lock jumped straight to the cap. Only the request whose increment creates the lock now raises the tier and reports `newLock`; a crossing that finds the lock already running (a burst, or a wrong password let through by a device cookie) still counts, but leaves the tier and the lock's end alone and sends no second lock notice. No more guesses get through than before. The same holds for the second-factor lock.
  
  Signing out every other device (`auth.sessions.revokeOthers`) now checks fresh authentication on the session it reads live from the store, not on the object the caller passed in.

## 0.4.0

### Minor Changes

- [#59](https://github.com/noctcore/auth/pull/59) [`a78168e`](https://github.com/noctcore/auth/commit/a78168e668f7add8256d44596bd29a6455f61dd1) Thanks [@Shironex](https://github.com/Shironex)! - Add the two-factor plugin, `@noctcore/auth/two-factor`: TOTP (RFC 6238) with replay protection, ten single-use recovery codes, trusted devices, step-up for sensitive actions, and enforcement on every session the library issues. A password reset of an account with a factor asks for a code or a recovery code. Secrets are encrypted through a `SecretCipher` the app provides.
  
  - New store port `TwoFactorStore`, with `twoFactorStoreConformance` and `MemoryTwoFactorStore` in `@noctcore/auth/testing`.
  - Plugin seam: `PluginContext` gains `keyedHash`, `requireFreshAuth` and `cookie`; `Throttle` gains `gateFactor` and `factorSucceeded`.
  - New mail events `two-factor-enabled`, `two-factor-disabled` and `recovery-code-used`, and new `two_factor.*` audit event types. A mailer or audit sink that switches over every type with a `never` check needs cases for them.
  - `issueSession` accepts the re-issue vias (`password-change`, `reauthenticate`, `revoke-others`, `email-verified`) only with an `inherit` the core read live from the store, for the same user, through the new `AuthCore.confirmLiveSession`, before the flow revoked anything. A revoked, expired, idle or hand-built session is refused, and `reauthenticate`, `changePassword` and `sessions.revokeOthers` answer `session_expired` (`session_not_active`) for one. `SessionManager` gains `findActive`.
  - A lock no longer resets the attempt counter: it holds the counter above the limit for as long as the lock lasts, and every further `limit + 1` failures under it raise the backoff tier (the running lock keeps its end time; a large parallel burst can raise the tier by more than one step). A request that read "no lock" just before another one set it is now refused, so a parallel burst over many connections gets no more than the budget, for the password lockout and the second factor alike.
  - **Rotating `secret` voids every recovery code** of the two-factor plugin, whose HMAC key is derived from it. After a rotation, have every user with a factor regenerate their recovery codes.
  - `twoFactor` checks `attempts` and `perIp` at creation: the limit must be a positive integer and the window positive.
  - `resetPassword` and `changePassword` check the new password against the policy before running the `beforePasswordReset` and `beforePasswordChange` hooks, so a refused password spends nothing a hook asked for.

## 0.3.0

### Minor Changes

- [#48](https://github.com/noctcore/auth/pull/48) [`ceaae4c`](https://github.com/noctcore/auth/commit/ceaae4c11e265c833e34375e829cf34205cb07a5) Thanks [@Shironex](https://github.com/Shironex)! - No flow awaits mail delivery any more. Sign-up, email verification (send and resend), password change, password reset, the reset request's job and the lockout notice from a password change call `mailer.send` and answer without awaiting the promise it returns, so a delivery that is slow, or never settles, no longer delays or hangs a response.
  
  Timing changes for consumers: responses no longer include the time the promise from `send` takes to settle, and a reset job run by `auth.jobs.processPasswordReset` resolves before its mail is delivered. The call to `send` is still on the response path: whatever `send` does before it returns its promise (rendering a template, opening a connection) counts toward the response time, and sign-up sends different templates for a taken and a new address. `send` must only enqueue, with templates built in a worker.
  
  Delivery from the library is at most once: each mail is handed over once, a `send` that throws or rejects is logged as `Mailer failed` and never retried, so retries belong to the app's queue. Enqueueing narrows the window in which mail can be lost but does not close it, because the enqueue itself is not awaited: a process that exits or a serverless instance frozen after the response can still lose it (no flush or `waitUntil` hook yet, [#50](https://github.com/noctcore/auth/issues/50)). Background sends have no timeout or cap, so give the enqueue a timeout ([#51](https://github.com/noctcore/auth/issues/51)).
  
  Type break: `PluginContext.mail` now returns `void` instead of `Promise<void>`. Plugin code that calls `.then` on `ctx.mail(...)`, or returns it where a `Promise<void>` is expected, no longer type-checks. Code that only awaited it still compiles (lint may flag the await of a non-promise) and behaves the same, minus the wait.
  
  The `afterRegister` hook stays awaited (an app may rely on its work being done before the answer), and its docs now say it runs only for a new address and so shows in sign-up timing: queue slow work instead of awaiting it. `registration.autoLogin` is documented as visible in sign-up timing too.
