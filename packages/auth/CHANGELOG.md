### Minor Changes

- [#213](https://github.com/noctcore/auth/pull/213) [`f82bf2d`](https://github.com/noctcore/auth/commit/f82bf2d61827d0616642aa73b8d8c4bf6a4c0178) Thanks [@Shironex](https://github.com/Shironex)! - New `PrismaUserStoreOptions.writeWhere` (also on `prismaStores`): a Prisma `where`, such as `{ closedAt: null }`, that a row must also match to take a new password hash (`setPasswordHash`), a verified mark (`markEmailVerified`) or an email change (`changeEmail`). It is combined with the store's own conditions through `AND`, in the same UPDATE, so an account your app closed on a column of its own refuses the write even when it was closed after your `beforePasswordReset` hook ran; the flows answer that as a refused write (`invalid_token` from a reset). Reads are unchanged, so login and lookups still find the row. An email revert (the `changeEmail` that also clears the password) is not guarded, since it only takes access away. Left out by default, so nothing changes unless you set it. The store checks the value when it is built and refuses with `AuthConfigError` anything but a plain object, and any guard that would match every row: an empty object anywhere in it (`{}`, `{ closedAt: {} }`), an `undefined` anywhere in it (Prisma reads it as no filter, so `{ orgId: process.env.ORG_ID }` with the variable unset would guard nothing), and an empty `AND` or `NOT` list (Prisma reads those as true). An empty `OR` matches no row, so it is allowed. A guard that matches every row in some other way (a condition every row meets) is not detected. The guard is copied and frozen, and each write gets a fresh copy, so neither the object you passed nor a Prisma extension that changes one call's `where` can change later writes. A column name Prisma does not know only shows at the first guarded write, which throws.
  
  The Prisma user store now rethrows a Prisma client error from `setPasswordHash`, `markEmailVerified`, `changeEmail` or the sign-up insert (`create`) as a `PrismaUserStoreError` without Prisma's message (keeping its `code`), since that message prints the whole call, the new password hash included, and a failed rehash is logged with it. This applies with or without `writeWhere`.
  
  In `@noctcore/auth`, an invitation sign-up (the invitations plugin's `register`) whose verified mark the store refuses now goes on with the account unverified: `afterRegister`, `onAccept` and the session see `emailVerified: false`, as the store holds it. It used to hand them `emailVerified: true` whatever the store answered. A mark that throws (a misspelled `writeWhere` column, an outage) is logged as `Marking an invited address verified failed` and treated the same way, so the membership and the session still follow; it used to fail the request with the invitation already spent.

- [#211](https://github.com/noctcore/auth/pull/211) [`64c6862`](https://github.com/noctcore/auth/commit/64c6862747a6802f510c647f3065c9293d0a3414) Thanks [@Shironex](https://github.com/Shironex)! - Four changes to password reset, for apps that run the whole reset flow on the package.
  
  **Fix: no reset link outlives a failed password write.** `resetPassword` and `changePassword` used to write the new hash first and void the reset links, codes and tickets after it, so a crash, a store error or a refused write left a code-mode ticket, or a link requested meanwhile, that could still set the password. They now void every reset token (and an email change started under the old password) before the write, and once more right after it, before the sessions end, so a link minted while the write ran dies even when ending the sessions throws. A failed or refused write leaves the old password and no link: the user asks again. The sweep after the write is tried twice. Whatever it does, every session is then ended, since the revocation is what signs an intruder out. If the sweep failed twice or the sessions could not be ended, the flow still writes `password.reset` (or `password.changed`) and sends the "password changed" mail for the write that happened, then throws the first failure; after a sweep that failed twice, a link minted during the write may stay live until it expires.
  
  **Behaviour change.** Once the hash is written, a failure to lift the lockout or to mark the address verified no longer throws: it is logged as `Step after a password write failed` (with the step and the user id) and `resetPassword` answers ok. The lock stays until it ends or an admin clears it, and the address stays unverified. `changePassword` now voids a pending email change (and every reset token) before it writes, so a change whose write then fails or is refused has still cancelled the pending email change.
  
  **New: `auth.inspectPasswordReset({ token, meta })`** checks a reset link (the ticket in code mode) without spending it and without mailing anything, for a reset page on load. A live link answers `ok({ userId, email, expiresAt, secondFactorRequired })`: only the account's id and address, since anyone holding the link sees the answer. An unknown, expired or spent one answers `invalid_token`, whichever it is. It counts on the `password-reset` door with `resetPassword`, so a page that checks its link and then resets spends two hits of that door (10 a minute per IP by default); raise `throttle.doors['password-reset']` if your page does both. It writes `password.reset_inspected` or `password.reset_inspect_failed` (no user id for an unknown token). `secondFactorRequired` comes from the new `passwordResetRequirements` hook (`({ user }) => ({ secondFactor?: boolean })`, any `true` wins), which the two-factor plugin answers for a confirmed factor; an app that demands its own factor in `beforePasswordReset` answers it there. The hook may also return a `refuse(...)`, which the check answers, so an account your app always refuses at reset looks the same on the page; an account in an email revert lockout answers `invalid_token`, as its reset does. `@noctcore/auth-trpc` adds `inspectPasswordResetInput` and `resetInspectionOutput`.
  
  **Type change in `@noctcore/auth/testing`:** the valid branch of `TokenRedemption` (from `OneTimeTokens.redeemLink`, `redeemCode` and `peekLink`) now has a required `expiresAt`. Code that builds a valid `TokenRedemption` by hand, a fake token service in your tests say, must add it.
  
  **New audit event `password.reset_issued`** (`userId`, `data.kind` `link` or `code`, the request's IP and user agent) when a reset job stores a link or code, before its mail is handed over, also when the job runs on your queue. Nothing is written for a request that sends nothing; those keep writing `password.reset_request_ignored`.
  
  **New: account mails say where the request came from.** Mail events sent to the address an account already holds carry an optional `meta: { ip, userAgent? }` (type `MailRequestMeta`): `password-reset`, `password-reset-code`, `password-changed`, `lockout`, `account-exists` (where it is the sign-up attempt's IP, so the holder sees where it came from), `email-changed`, `email-change-reverted` and the two-factor plugin's mails. `PasswordResetJob` gains an optional `userAgent`, captured at the request, so the reset mail and the job's audit rows carry the request's IP and user agent when the job runs on a queue worker. Mails to an address the request names itself (`verify-email` after a sign-up, `email-change-confirm` to the new address) and mails to someone other than the account (`email-change-in-use`, `invitation`) never carry it, since nobody has proven that address belongs to the account. A mailer that ignores `meta` keeps working; if your queue stores the whole event, it now stores the IP and user agent too. Jobs queued before this release have no `userAgent` and run as before.

- [#227](https://github.com/noctcore/auth/pull/227) [`69fcecb`](https://github.com/noctcore/auth/commit/69fcecbe0bb04ff5942b1b63e0bd5e0b9181efb8) Thanks [@Shironex](https://github.com/Shironex)! - New session option `session.requireFreshAuth: { revokeSession?: boolean; revokeOtherSessions?: boolean }`, both `true` by default, so nothing changes unless an app sets it. With `revokeSession: false`, `sessions.revoke` ends another device's session without a credential proof inside `freshAuthAge`; with `revokeOtherSessions: false`, `sessions.revokeOthers` signs out every other device without one. The door still needs a live session of the same user (`session_expired` otherwise), and `freshAuthAge` and every other door (the email change, two-factor enrollment and management, step-up) keep their check. Startup refuses a `requireFreshAuth` that is not an object, and a value under it that is not `true` or `false`.
  
  `sessions.revoke` now answers `{ revoked: true, sessionId }` for a session it ended, where `sessionId` is the session's store key, the same id `onSessionsRevoked` reports, so an app can close that session's live connections right after the call. A handle that names no session of the caller still answers `{ revoked: false }`, with no id. The store key is for the server only: if your route sends `result.value` to the client as it is, send `{ revoked: result.value.revoked }` instead, as the examples now do. The tRPC adapter's `revokedOutput` already strips the id. The new type `RevokeSessionOutcome` names the answer.

- [#212](https://github.com/noctcore/auth/pull/212) [`3f39f17`](https://github.com/noctcore/auth/commit/3f39f176891f4d061e09b401a5beace4297230e7) Thanks [@Shironex](https://github.com/Shironex)! - New lockout option `throttle.lockout.sessionProofs: 'lockout' | 'door'`, default `'lockout'`, so nothing changes unless an app sets it.
  
  By default `reauthenticate` and `changePassword` prove the current password through login's lockout: a wrong one spends the account's sign-in budget, can lock the account, sends the lock mail and counts toward the permanent tier, and a correct one under a lock needs a free device slot. So whoever holds a session, a stolen one included, can lock the owner out of sign-in by guessing wrong current passwords.
  
  With `'door'`, each door's own per-user limit (`throttle.doors`, `password-change` and `reauthenticate`, 5 per 5 minutes by default) is the only budget. A wrong password writes `password.change_failed` and touches no lockout counter (no lock, no lock mail, nothing toward the permanent tier), and a temporary lock does not refuse a correct password from a live session. The permanent tier refuses these doors as before, which is only with `permanent.trustedDevices: false`. The trade-off: guesses from a stolen session then run at the doors' rate (each door has its own key: 1440 a day per door, 2880 across both, with the defaults) and never lock anything, so keep the door limits tight. `'door'` covers password guesses only: wrong second-factor codes at a step-up still count in the factor's budget, so a stolen session can still lock the factor, and each factor lock counts toward the permanent tier. `Throttle` gains a `sessionProofs` field, and startup refuses any other value.

Every count now goes through a guard that logs `Metrics port failed` with the counter's name, so a password change or reset still sends its "password changed" mail and answers its real outcome, and a background timeout no longer turns into an uncaught exception.

Treat that throw as signed out and send the user to sign in with the new password.

It now also refuses `OR: []` inside a `NOT` (`{ NOT: { OR: [] } }` matches every row, also through an `AND` inside the `NOT`) and a list with an empty slot. `every: {}` and `is: {}` stay refused: ask for a related row with `isNot: null`.

- [#233](https://github.com/noctcore/auth/pull/233) [`3978bf3`](https://github.com/noctcore/auth/commit/3978bf3469a6e0a025d1142a60378a98a2253c87) Thanks [@Shironex](https://github.com/Shironex)! - The two-factor plugin has three new flows for apps that run part of a sign-in themselves.
  
  - `auth.twoFactor.challenge({ userId, rememberMe?, epoch?, meta })` starts the second-factor challenge for a sign-in your app authenticated itself (an identity provider, a magic link of its own). It answers `null` when no factor is due (issue your own session then), or the same `{ challenge, methods }` a password login gives, finished with `verifyChallenge`. Each call counts on the plugin's `perIp` limit.
  - `auth.twoFactor.verifyProof({ userId, proof?, action, meta })` checks a second factor for a user your flow identified without a session (an app-owned reset, an invitation that overwrites an account). It uses the challenge's attempt budget, lockout, per-IP limit, replay guard and recovery-code spend, so it is never a faster way to guess codes. With a proof, a user with no confirmed factor, or no such user, answers `invalid_second_factor` like a wrong code. A code for a user without a confirmed factor never locks the account or climbs the permanent lockout tier. Without a proof it answers `{ proved: false }` when nothing is needed and `second_factor_required` when the user has a factor, which reveals whether the account has one, so call it (with or without a code) only for someone who already proved control of the account. Every call counts on the plugin's `perIp` limit. It never issues or touches a session.
  - `auth.twoFactor.reset({ userId, actor?, meta })` is an admin's reset of another user's factor: it deletes the factor, the recovery codes and the trusted devices, writes the new `two_factor.reset` audit event (with `data.actor`), and mails the owner the existing `two-factor-disabled` mail, now with `reset: true`. It trusts its caller: call it only after your own checks. Your existing `two-factor-disabled` template will tell the user they turned the factor off themselves until it reads `reset`. A step-up proof a session already holds survives the reset; revoke the user's sessions after a takeover.
  
  A login whose `sessionAttributes` fail your session attribute schema after a correct password now answers `invalid_credentials` (reason `invalid_session_attributes`) with a `login.failure` row, like a wrong password, instead of `forbidden`, so the answer no longer tells a caller the password was right. The schema error is still logged for you. Other ways of issuing a session still answer `forbidden`.

- [#231](https://github.com/noctcore/auth/pull/231) [`a37f5b2`](https://github.com/noctcore/auth/commit/a37f5b286d3c32196364f04be61514ec4e1afdcd) Thanks [@Shironex](https://github.com/Shironex)! - With a second-factor plugin, the `beforeSessionCreate` hooks (and the `sessionAttributes` hooks that feed them) now also run after a correct password, before any challenge is made (`via: 'password'`, `beforeChallenge: true`). An account a hook refuses gets the refusal's code (`invalid_credentials` by default) and a `login.failure` row with the hook's reason, and no challenge, so it never learns its password was right. The hooks run again for the session (`via: 'second-factor'`, or `'password'` when no challenge is due), so with the plugin every password login runs them twice.
  
  A correct password that a `beforeSessionCreate` hook refuses at login now counts as a wrong password in the lockout, with or without a plugin: it no longer clears the per-address counter or rehashes the password, so the lockout's next answer (with `revealLocked`, `account_locked` against `invalid_credentials`) cannot tell the two apart.
  
  An app's own re-issue of a session can now pass the two-factor plugin. Issue it with your own `via` and the caller's session as `inherit` (and its `authenticatedAt`, unless your flow just proved the password). The core checks that the session is live and the same user's (or takes the object the new `PluginContext.confirmLiveSession` returned before your flow ended sessions) and refuses it as `session_expired` otherwise; that check is new for every `via` of your own that passes an `inherit`. The new session's attributes, remember-me and cookie shape come from the stored copy, and a session the core read itself is fenced at its epoch, so a revoke-all that lands before the mint refuses it. The `beforeSessionCreate` hooks see it as `reissueOf`. For a user with a confirmed factor, the plugin lets it through only when that session was created after the factor's enrollment window closed, or holds an open step-up; without `inherit` it is refused as before. This is a best effort, not a proof that the session descends from a proof of the factor: a pre-enrollment session that one of the core's re-issues renewed after the window, or a login that raced the enrollment, passes it. Turn the factor on with `revokeOtherSessions: true` to end those. The core's own re-issues behave as before.

- [#235](https://github.com/noctcore/auth/pull/235) [`167d3b9`](https://github.com/noctcore/auth/commit/167d3b95af7309202a6ee3a686f52856ae2b96ab) Thanks [@Shironex](https://github.com/Shironex)! - The two-factor plugin has two new options.
  
  - `enrollmentWindow` (default `'10m'`, positive, at most `'24h'`) sets how long a pending secret from `enroll` accepts its confirmation code; `Enrollment.expiresAt` follows it. Confirming still needs a fresh password proof, and an enrollment challenge still ends with the challenge (5 minutes). The window also dates when a factor counts as set up for an app's own re-issue of a session, so shrinking it while enrollments are pending lets a session created between the new and the old end pass; turn factors on with `revokeOtherSessions: true` if you shrink it.
  - `enforcementStanding: 'at-issue'` or `{ mode: 'at-issue', version?, maxAge? }` (with `enforcement`; default `'live'`, unchanged) also decides the standing when a session is issued. A session issued unrestricted (a confirmed factor, or no factor required) is stamped in the `twoFactorStanding` session attribute and validates without reading the factor, the user or the policy until the stamp is `maxAge` old (default `'1d'`, at most `'30d'`); every other session is read live as before. The stamp is a keyed hash of the user, the version, the revocation epoch and the issue time, so a stamp copied from another session, user or store does not count, and a session whose stamp one of your own `sessionAttributes` hooks replaced is refused. After you require a factor of a user or change their policy, call the new `twoFactor.refreshStanding({ userId })`: it ends the user's sessions whenever `enforcement` is on, in either mode, so a stamp from an earlier spell under `'at-issue'` cannot come back after a rollback. A new `version` sends every older stamp back to live reads after a change to many users. A change you neither refresh nor version reaches a stamped session within `maxAge` (`sweepUnenrolled` still backs this up). With a session attribute schema, let `twoFactorStanding` through as an optional string: `createAuth` refuses a schema that refuses it.
  
  With `enforcement` on, `twoFactor.reset` of a confirmed factor now also ends the user's sessions, in either mode. The revocation reasons `TWO_FACTOR_STANDING_REVOCATION` (`two-factor-standing`) and `TWO_FACTOR_RESET_REVOCATION` (`two-factor-reset`) are exported from `@noctcore/auth/two-factor`. Plugins get `parseSessionAttributes(value)` on their context, to check at startup that the app's session attribute schema keeps what they add; a hand-written `PluginContext` stand-in has to add it.

- [#230](https://github.com/noctcore/auth/pull/230) [`7d65a69`](https://github.com/noctcore/auth/commit/7d65a69903b38638a6640b7b89b32f65495edde3) Thanks [@Shironex](https://github.com/Shironex)! - A password write that throws may still have committed (the connection dropped after the commit). `resetPassword` and `changePassword` now end every session in that case too, as after any write, before they write `password.reset_failed` or `password.change_failed` (reason `write_failed`) and rethrow. Ending the sessions when the write did not land costs a sign-in; keeping them when it did would keep an intruder in. After such a throw the account may have either password: tell the user to try the new one. If ending the sessions fails too, that failure is logged as `Closing after a password write that threw failed`, and the write's own error is the one thrown.
  
  An async metrics port (`count: async () => ...`, which TypeScript accepts as `Metrics`) that rejects is now caught and logged as `Metrics port failed`, in the flows and in the background timer, instead of becoming an unhandled rejection that ends a Node process by default. A logger that throws while that failure is reported is ignored.
  
  `PrismaUserStore` `writeWhere` now works out from the guard's shape which conditions match no row (`OR: []`, `in: []`) and carries that through `AND`, `OR`, `NOT`, `not`, `some`, `none`, `is` and `isNot`. A condition that then matches every row is refused at boot, such as `{ NOT: { OR: [{ OR: [] }] } }`, `{ NOT: { closedAt: { in: [] } } }`, `{ m: { none: { OR: [] } } }`, `{ p: { isNot: { OR: [] } } }` or `{ closedAt: { notIn: [] } }` (so a block list built from configuration fails boot while it is empty). This is a best-effort extra refusal, not a proof that a guard narrows: some match-all forms still pass, and the configuration reference lists examples. The store does not know the model: a misplaced relation filter or an unknown column still fails on the first guarded write, and a to-one relation filtered without `is` reads as a column, so write `is: { ... }`. Values JSON cannot write (a bigint, a Decimal, bytes, `Prisma.DbNull`) are read without throwing, and the check only ever adds a refusal: it never fails boot on a value it cannot read.

## 0.9.0

### Minor Changes

- [#200](https://github.com/noctcore/auth/pull/200) [`ad9f1eb`](https://github.com/noctcore/auth/commit/ad9f1ebbb190fe3908a8280f7808e9685e9601e3) Thanks [@Shironex](https://github.com/Shironex)! - Two new lockout options, both off by default so nothing changes unless an app sets them.
  
  `throttle.lockout.countSuccesses` (default `true`): when `false`, a correct password's slot in the account-wide budget (`perAccount`) comes back, so only failures count and a user who signs in many times within the window is no longer locked. The slot comes back when the sign-in completes (a session issued with `via: 'password'` or `via: 'second-factor'` and no `inherit`), not when the password proves right, so a correct password that opens a second-factor challenge keeps spending until the factor is proved. At `reauthenticate` and `changePassword` it comes back right after the correct password, since the caller already holds a session. A completion hands back at most one slot, and never more slots than correct passwords reserved in the current account-wide window, however many sign-ins complete at once. Refunds are matched by count, not to the attempt that earned them: a completion that reserved nothing of its own (a challenge opened in an earlier window, a device sign-in) can take a slot another correct password in the window is owed. Slots owed in a window that ended, including one a lock ended, never come back in the next. Not atomic: a completion racing the first attempt of a new window, or racing a password reset, can hand back one slot of the new budget. `Throttle` gains `refundSuccess` and a `countSuccesses` field.
  
  `throttle.lockout.durations`: a list of lock durations used in place of `baseLock` and `maxLock`. Lock N in a row lasts entry N and the last entry repeats, so `['15m', '1h']` locks for 15 minutes, then an hour each time after. The two-factor plugin's factor locks climb the same ladder. Startup refuses an empty list, an entry that is not a duration or is zero, and `durations` together with `baseLock` or `maxLock`.
  
  With `revealLocked`, a lock that a racing request set and that can no longer be read is answered as one of the first lock's length: the first `durations` entry, or `baseLock` capped at `maxLock`. Before, it was `baseLock` uncapped, so the answer changes only for an app whose `baseLock` is longer than its `maxLock`, where it now matches the lock actually set. Such a configuration is still accepted (every lock is capped at `maxLock`), since refusing it at startup would stop apps that boot today.
  
  The docs now say that `context.recordFailedProof` must be given only an account the request is already acting on, and that wrong codes while enrolling a factor or at a step-up count toward the permanent tier like wrong codes at login.

- [#198](https://github.com/noctcore/auth/pull/198) [`d83c560`](https://github.com/noctcore/auth/commit/d83c5608d7368596f602c1b86bf61a7ef6376181) Thanks [@Shironex](https://github.com/Shironex)! - With `throttle.lockout.permanent` on, the count of locks in a row toward the permanent tier now starts over only when a sign-in completes: a session issued with `via: 'password'` or `via: 'second-factor'` and no `inherit`, so every factor is proved. Before, a correct password reset it before the `loginChallenge` hooks ran, so an attacker who held the password could reset the climb before every round of guessed codes and never reach the tier. The two-factor plugin's factor locks now count toward the tier too, in the same count as the password locks, and the permanent lock they bring about is carried out like a password one (the `lockout` mail, the `account.locked_permanently` audit row, the end of the sessions and `onPermanentLock`).
  
  New on the plugin context (`auth.context`): `recordFailedProof({ userId | email, meta })` counts a failed proof of the app's own (its own second factor, a PIN) in the account-wide budget and carries a lock it sets out like a password lock, where `throttle.recordFailure` only counted and its locks reached nobody. `escalateLock({ userId, meta })` counts a lock the app's own gate set toward the permanent tier. `Throttle` gains `signInCompleted` and `escalate`; `LockTarget` now lives with the throttle's types (still exported from the package root).
  
  **Behaviour change:** with the permanent tier on, accounts can reach it sooner than before. A correct password that opens a second-factor challenge, and a correct password at `reauthenticate` or `changePassword`, no longer start the count over; only a completed sign-in or a completed password reset does. Locks of the two-factor plugin's factor now count toward the tier, so a user with a second factor who keeps mistyping codes can be locked for good after `afterLocks` locks in a row, until an admin calls `auth.lockout.clear`. An app with its own second factor that finishes it through `issueSession` should issue with `via: 'second-factor'` so the sign-in counts as completed. Code that implements `PluginContext` itself (rather than taking it from `createAuth`) must add `recordFailedProof` and `escalateLock`. With the tier off, nothing changes.

## 0.8.0

### Minor Changes

- [#172](https://github.com/noctcore/auth/pull/172) [`c3ef03e`](https://github.com/noctcore/auth/commit/c3ef03e924fdc9ef106868ddd6b0ccebbf49bfe2) Thanks [@Shironex](https://github.com/Shironex)! - `clientIp` now checks the `X-Forwarded-For` entry it picks, with a hop count or a proxy list: a port, brackets and an IPv6 zone id are stripped (`203.0.113.9:51234` reads as `203.0.113.9`, `[2001:db8::1]:443` as `2001:db8::1`, `fe80::1%eth0` as `fe80::1`), and what is left must be exactly one IPv4 or IPv6 address. Before, the entry was returned as written, so behind a gateway that writes the source port every connection got its own per-IP rate-limit bucket, and a proxy's junk reached audit events and session lists. With a proxy list, an entry that is not an address is never trusted, so the walk stops there. The NestJS and tRPC adapters read the IP through `clientIp` and get the same rule.
  
  **Behaviour change:** an entry that used to be returned as written can now give another answer. An entry with a port, brackets or a zone id gives the bare address, so per-IP counters and audit rows behind such a gateway move to the bare address (old per-port counters simply expire). An entry that is still not one IP (`not-an-ip`, port 0 or a port above 65535, a bracketed IPv4 address, an IPv4-mapped IPv6 address with a port and no brackets) is never returned: the socket address stands in for it, or `unknown` when there is none, so every such request from one proxy now shares that proxy's bucket.
