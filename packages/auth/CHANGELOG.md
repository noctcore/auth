# @noctcore/auth

## 0.7.0

### Minor Changes

- [#136](https://github.com/noctcore/auth/pull/136) [`1a9c977`](https://github.com/noctcore/auth/commit/1a9c977b4db46fbb4d8be774dffad7f0cdbc7950) Thanks [@Shironex](https://github.com/Shironex)! - A new `previousSecret` option keeps the secret a rotation replaced (or several, newest first) for a grace window, so rotating `secret` no longer voids every pending code, trusted-device cookie, session handle and two-factor recovery code at once. Without it, behaviour is unchanged.
  
  - Every key is derived from each secret. Signing, keyed hashing for storage and new cookies use only the current secret; verification tries the current key, then each previous one, in constant time per candidate. A code from before the rotation is still found and counts one attempt per try, a device cookie from before still lets a correct password through a lock (and the next sign-in writes a new one), a handle from before still revokes its session (the next list shows the new one), and a recovery code from before is still spent once. Invitations stored under the keyed hash used before 0.6 are found under a previous secret too.
  - Startup fails with `AuthConfigError` when a previous secret equals `secret` or another previous one, or is shorter than 32 bytes.
  - Plugin context: new `keyedHashes(purpose, message)` (the keyed hash under each secret, current first) and `matchesSessionHandle(sessionId, handle)`.
  - Remove `previousSecret` once the longest-lived value has expired: the trusted-device max age (30 days by default). Recovery codes never expire, so ask users to make a new set before removing it. The README walks through the procedure.

## 0.6.0

### Minor Changes

- [#93](https://github.com/noctcore/auth/pull/93) [`5ef423f`](https://github.com/noctcore/auth/commit/5ef423f29ac787f97ec06e60e4bbefb672907732) Thanks [@Shironex](https://github.com/Shironex)! - The NestJS and tRPC adapters now work with a desktop shell served from its own scheme (such as `app://desktop`).
  
  - The CSRF cookie (`__Host-csrf`), the pre-session cookie (`__Host-presession`) and the blank cookie that clears a refused session take the session cookie's `SameSite` for the request's `Origin`, instead of a fixed `Lax`. A cookie written next to a new session takes that session cookie's own value. With the default `session.cookie.sameSite` (`'lax'`) nothing changes. An app that sets it to `'strict'`, `'none'` or a function now gets the same answer on these cookies too.
  - New `csrf.crossSiteOrigins` option in both adapters: exact origins whose cross-site requests are accepted. A listed origin passes the `Origin` check, and its `Sec-Fetch-Site: cross-site` requests pass the fetch-metadata check. The double-submit token is still required. Matching is exact (scheme, host and port). At boot, an entry fails if it is a wildcard, `null`, has no host, or carries a path, query, fragment or user info. The list is empty by default, so behaviour is unchanged until you name an origin. Trust a listed origin as much as your own: see the threat model.
  - Core: `resolveSameSite(config, origin)` gives the session cookie's `SameSite` for an origin (used by every cookie that travels with it), `verifyFetchSite` takes optional `origin` and `crossSiteOrigins` inputs, and `assertExactOrigins(origins, option)` checks an origin allowlist at boot. Each adapter also refuses `SameSite=None` when its cookies are not Secure, even if the cookie config claims they are.

- [#127](https://github.com/noctcore/auth/pull/127) [`89932e2`](https://github.com/noctcore/auth/commit/89932e2e1ee9c903e19db79643a58352263124d8) Thanks [@Shironex](https://github.com/Shironex)! - The `standard` (default) and `ascii` email policies take only a host name as the domain, as `unicode` does: letters, digits and inner hyphens per label (at most 63 characters), no empty label, and a last label that is not all digits. They used to check only for one inner dot, so `a@exa_mple.com`, `a@-example.com`, `a@example..com`, `a@127.0.0.1` and `a@127.1` were accepted; they are now answered `invalid_email`.
  
  Behaviour change: a stored address whose domain is not a host name (an IPv4 address, an underscore or another character outside a host name, an empty label, a label that starts or ends with a hyphen or is longer than 63) can no longer sign in, reset or be found by address, and a pending invitation to it cannot be accepted. An outstanding email change or verification token that names such an address can no longer be redeemed either: the flows normalise the address again when the token is used and refuse it (they fail closed), so the user has to start the change or request a new mail with a valid address. Find such rows before upgrading and rewrite or remove them. In PostgreSQL, on your user table and on `AuthInvitation`:
  
  ```sql
  SELECT id, email FROM users -- your user table
  WHERE split_part(email, '@', 2) !~ '^([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$'
     OR split_part(email, '@', 2) ~ '\.[0-9]+$';
  
  SELECT id, email FROM "AuthInvitation"
  WHERE split_part(email, '@', 2) !~ '^([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$'
     OR split_part(email, '@', 2) ~ '\.[0-9]+$';
  ```
  
  On another store, look for the rows where `auth.normalizeEmail(email)` is not exactly the stored email, which finds these too (see the configuration reference).
  
  Upgrade note for the `unicode` policy: what it accepts depends on the runtime's URL parser and Unicode tables (Node, Bun, an edge runtime), so uniqueness holds on one runtime, but an address stored under one runtime can be refused after a runtime upgrade that remaps one of its characters.
  
  Docs: `adoptLegacySessions` signals a lost adoption race on the store it returns, so pass that result directly to `createAuth`; a store of your own that wraps it hides the signal and the user is signed out again. Wrap the package's store before `adoptLegacySessions` instead.

- [#122](https://github.com/noctcore/auth/pull/122) [`a78835e`](https://github.com/noctcore/auth/commit/a78835e018c59fb82863bcea122cf7d6fb4f6c82) Thanks [@Shironex](https://github.com/Shironex)! - Hardens email normalisation after the 0.6 review.

  - The `unicode` policy refuses an input longer than 1016 characters before any Unicode normalisation; the 254-byte limit still applies to the result.
  - A custom normaliser that throws on the startup check for distinct mailboxes now fails `createAuth` with `AuthConfigError` (the original error as `cause`), like every other startup check.
  - When the user store returns a row whose stored email is not exactly the normalised address, the core still treats it as not found and now logs a warning with the user id, never the address, so rows written in another spelling show up in the logs. Behind a case- or accent-insensitive collation the warning repeats on every lookup of such a row and can be noisy until the rows are rewritten.

- [#98](https://github.com/noctcore/auth/pull/98) [`1ac8ef2`](https://github.com/noctcore/auth/commit/1ac8ef25814bfed484dd94cd45f55ee107407712) Thanks [@Shironex](https://github.com/Shironex)! - Email normalisation is now configurable with `email.normalize`. The default (`'standard'`) is unchanged and stores byte-identical spellings, so existing data keeps matching.
  
  - `'ascii'`: the same spelling as the default, but an address with a non-ASCII character is answered with the new public code `email_not_ascii` (sign-in still answers `invalid_credentials`, with `email_not_ascii` as the audited reason). The tRPC adapter maps it to `BAD_REQUEST`.
  - `'unicode'`: keeps Unicode addresses. NFC, then lowercase of the domain and the local part (the Greek final sigma folded to the plain one in the local part, so case variants of a Greek address stay one account; a domain keeps a typed final sigma, as IDNA2008 does). Refuses invisible, bidi, control, unassigned and compatibility characters, punycode labels, any part that mixes scripts (the Chinese, Japanese and Korean mixes with Latin are allowed), the dotless i, the IPA Extensions block (U+0250 to U+02AF) and a combining dot above on i or j.   Lookups by address are now exact on the core's side for every policy: a user row whose stored email is not exactly the normalised address asked for counts as not found, so a store behind a case- or accent-insensitive collation cannot reach one account under several spellings with separate lockout and rate-limit keys. `userStoreConformance` gains the case "different spellings must not match", and the plugin context gains `findCredentialByEmail`. A binary or accent-sensitive collation on the email column is recommended (see the auth-prisma README).
  
  Changing the policy on a live database needs a data migration first: rows stored under the old policy no longer match. The package does not migrate data; see the configuration reference.
  
  Upgrade note: because lookups are now exact, a row whose email was written outside the flows (an import, an admin tool, a seed) in a spelling the normaliser would not produce is unreachable, even under the default policy: its owner can no longer sign in, reset or be found by address. Before upgrading, find the rows where the stored email differs from `auth.normalizeEmail(email)` (for the default policy, any row with uppercase letters, surrounding whitespace or a non-ASCII character), then rewrite them or merge duplicates.
