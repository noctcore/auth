## 0.10.0

### Minor Changes

- [#213](https://github.com/noctcore/auth/pull/213) [`f82bf2d`](https://github.com/noctcore/auth/commit/f82bf2d61827d0616642aa73b8d8c4bf6a4c0178) Thanks [@Shironex](https://github.com/Shironex)! - New `PrismaUserStoreOptions.writeWhere` (also on `prismaStores`): a Prisma `where`, such as `{ closedAt: null }`, that a row must also match to take a new password hash (`setPasswordHash`), a verified mark (`markEmailVerified`) or an email change (`changeEmail`). It is combined with the store's own conditions through `AND`, in the same UPDATE, so an account your app closed on a column of its own refuses the write even when it was closed after your `beforePasswordReset` hook ran; the flows answer that as a refused write (`invalid_token` from a reset). Reads are unchanged, so login and lookups still find the row. An email revert (the `changeEmail` that also clears the password) is not guarded, since it only takes access away. Left out by default, so nothing changes unless you set it. The store checks the value when it is built and refuses with `AuthConfigError` anything but a plain object, and any guard that would match every row: an empty object anywhere in it (`{}`, `{ closedAt: {} }`), an `undefined` anywhere in it (Prisma reads it as no filter, so `{ orgId: process.env.ORG_ID }` with the variable unset would guard nothing), and an empty `AND` or `NOT` list (Prisma reads those as true). An empty `OR` matches no row, so it is allowed. A guard that matches every row in some other way (a condition every row meets) is not detected. The guard is copied and frozen, and each write gets a fresh copy, so neither the object you passed nor a Prisma extension that changes one call's `where` can change later writes. A column name Prisma does not know only shows at the first guarded write, which throws.
  
  The Prisma user store now rethrows a Prisma client error from `setPasswordHash`, `markEmailVerified`, `changeEmail` or the sign-up insert (`create`) as a `PrismaUserStoreError` without Prisma's message (keeping its `code`), since that message prints the whole call, the new password hash included, and a failed rehash is logged with it. This applies with or without `writeWhere`.
  
  In `@noctcore/auth`, an invitation sign-up (the invitations plugin's `register`) whose verified mark the store refuses now goes on with the account unverified: `afterRegister`, `onAccept` and the session see `emailVerified: false`, as the store holds it. It used to hand them `emailVerified: true` whatever the store answered. A mark that throws (a misspelled `writeWhere` column, an outage) is logged as `Marking an invited address verified failed` and treated the same way, so the membership and the session still follow; it used to fail the request with the invitation already spent.

- [#228](https://github.com/noctcore/auth/pull/228) [`0d71b22`](https://github.com/noctcore/auth/commit/0d71b22555244e1ea6338d600136cf49670daf4e) Thanks [@Shironex](https://github.com/Shironex)! - A metrics port that throws no longer throws out of a flow. Every count now goes through a guard that logs `Metrics port failed` with the counter's name, so a password change or reset still sends its "password changed" mail and answers its real outcome, and a background timeout no longer turns into an uncaught exception.
  
  A password reset whose sweep before the write, or whose write itself, throws now writes `password.reset_failed` (reason `write_failed`) before it throws, so the spent link is on the audit trail.
  
  If `changePassword` throws after the write (ending the sessions failed, or the sweep after the write failed twice), the password has changed and the caller's session may already be revoked, with no new session issued. Treat that throw as signed out and send the user to sign in with the new password.
  
  `PrismaUserStore` `writeWhere` now accepts `some: {}` and `none: {}` under a to-many relation (`{ memberships: { some: {} } }`), which narrow the write. It now also refuses `OR: []` inside a `NOT` (`{ NOT: { OR: [] } }` matches every row, also through an `AND` inside the `NOT`) and a list with an empty slot. `every: {}` and `is: {}` stay refused: ask for a related row with `isNot: null`.

- [#230](https://github.com/noctcore/auth/pull/230) [`7d65a69`](https://github.com/noctcore/auth/commit/7d65a69903b38638a6640b7b89b32f65495edde3) Thanks [@Shironex](https://github.com/Shironex)! - A password write that throws may still have committed (the connection dropped after the commit). `resetPassword` and `changePassword` now end every session in that case too, as after any write, before they write `password.reset_failed` or `password.change_failed` (reason `write_failed`) and rethrow. Ending the sessions when the write did not land costs a sign-in; keeping them when it did would keep an intruder in. After such a throw the account may have either password: tell the user to try the new one. If ending the sessions fails too, that failure is logged as `Closing after a password write that threw failed`, and the write's own error is the one thrown.
  
  An async metrics port (`count: async () => ...`, which TypeScript accepts as `Metrics`) that rejects is now caught and logged as `Metrics port failed`, in the flows and in the background timer, instead of becoming an unhandled rejection that ends a Node process by default. A logger that throws while that failure is reported is ignored.
  
  `PrismaUserStore` `writeWhere` now works out from the guard's shape which conditions match no row (`OR: []`, `in: []`) and carries that through `AND`, `OR`, `NOT`, `not`, `some`, `none`, `is` and `isNot`. A condition that then matches every row is refused at boot, such as `{ NOT: { OR: [{ OR: [] }] } }`, `{ NOT: { closedAt: { in: [] } } }`, `{ m: { none: { OR: [] } } }`, `{ p: { isNot: { OR: [] } } }` or `{ closedAt: { notIn: [] } }` (so a block list built from configuration fails boot while it is empty). So are `some` and `none` (or `is` and `isNot`) of one condition on one relation, on one key or split over the direct entries of one `OR`. This is a best-effort extra refusal, not a proof that a guard narrows: some match-all forms still pass, and the configuration reference lists examples. The store does not know the model: a misplaced relation filter or an unknown column still fails on the first guarded write, and a to-one relation filtered without `is` reads as a column, so write `is: { ... }`. Values JSON cannot write (a bigint, a Decimal, bytes, `Prisma.DbNull`) are read without throwing, and the check only ever adds a refusal: it never fails boot on a value it cannot read.

- [#188](https://github.com/noctcore/auth/pull/188) [`3c61c82`](https://github.com/noctcore/auth/commit/3c61c822485da0e16785498bfe4694eabec3565c) Thanks [@Shironex](https://github.com/Shironex)! - A one-time code check now counts its attempt on the code it read, and a link extend never revives a link that expired meanwhile.
  
  - `TokenStore` has a new optional `incrementAttemptsByHash(purpose, hash, max)`: the capped attempt increment of `incrementAttempts`, on the token with that hash only, null when that token is gone or at the cap. `MemoryTokenStore` and `PrismaTokenStore` (a guarded `update`, no schema change) implement it. A code resent between a check's read and its count used to be charged for the guess at the old code, and the old code answered as if it had been compared; the resent code now keeps every attempt. A store without it still works and counts by user and purpose, as before.
  - `extendExpiry` now takes the time as a fourth argument and refuses a token whose expiry is not after it, in the same update. `MemoryTokenStore` and `PrismaTokenStore` implement it. The consume and put fallback of `extendLink` (for a store without `extendExpiry`) no longer puts back a link that expired between its check and the put.
  - The fallback's two remaining gaps are documented on `TokenStore` and in the store adapter guide: its put replaces a link of the same user and purpose issued in between, and a put that fails after the consume loses the link.
  - `tokenStoreConformance` has three new cases: `extendExpiry` never extends an expired token, and `incrementAttemptsByHash` counts only the token with that hash and never passes the cap under concurrent callers.
  
  **Behaviour change:** a code check whose code was replaced by a resend, or spent by a concurrent winner, before its attempt was counted now answers `consumed` (a guess at a code that no longer exists is never compared), where it answered `mismatch`, `exhausted` or, through the old count, charged the new code. The flows report it with the `consumed` reason (`reset_code_consumed`, `verification_consumed`, `email_change_consumed`), all still `invalid_token`. For store authors: `tokenStoreConformance` now expects `incrementAttemptsByHash` and the `now` argument of `extendExpiry`, so a third-party `TokenStore` fails the new cases until it adds them. Implement both as updates guarded on `(purpose, hash)` (and on `expiresAt` after `now` for the extend) that never insert.

- [#174](https://github.com/noctcore/auth/pull/174) [`10baeb2`](https://github.com/noctcore/auth/commit/10baeb28d39b11343d229c2db371f5df32513791) Thanks [@Shironex](https://github.com/Shironex)! - One-time codes and links no longer lose a race with a concurrent request.
  
  - A submitted code that is expired, exhausted or at its last wrong guess is now removed by the hash that was read (`consume`), not by user and purpose. A code resent between the submit's read and its delete used to be removed with it and then answered `unknown`; it now stays valid.
  - `OneTimeTokens.extendLink` no longer writes a link back with `put`. When the link was spent between the read and the write (two clicks on one revert link, one taking the lockout branch while the other spends it), the spent link used to be stored again with a far future expiry. It now stays spent.
  - `TokenStore` has a new optional `extendExpiry(purpose, hash, expiresAt, now)`: it moves the expiry of the token with that hash only while it still exists and has not expired, in one step, and returns whether it changed one. `MemoryTokenStore` and `PrismaTokenStore` (a guarded `update`, no schema change) implement it. A store without it still works: `extendLink` then consumes the link and puts it back, which never revives a spent link but hides the link for one round trip.
  - `tokenStoreConformance` has three new cases: a consume by the hash of a replaced token leaves the replacement, and `extendExpiry` extends a live token, creates nothing and never brings back a consumed one, also when racing the consume.
  
  Behaviour change for store authors: `tokenStoreConformance` now expects `extendExpiry`, so a third-party `TokenStore` without it fails the two `extendExpiry` cases until it adds one. Implement it as an update guarded on `(purpose, hash)` that never inserts (no upsert). Nothing changes at runtime for such a store beyond the fallback above.

- [#98](https://github.com/noctcore/auth/pull/98) [`1ac8ef2`](https://github.com/noctcore/auth/commit/1ac8ef25814bfed484dd94cd45f55ee107407712) Thanks [@Shironex](https://github.com/Shironex)! - Email normalisation is now configurable with `email.normalize`. The default (`'standard'`) is unchanged and stores byte-identical spellings, so existing data keeps matching.
  
  - `'ascii'`: the same spelling as the default, but an address with a non-ASCII character is answered with the new public code `email_not_ascii` (sign-in still answers `invalid_credentials`, with `email_not_ascii` as the audited reason). The tRPC adapter maps it to `BAD_REQUEST`.
  - `'unicode'`: keeps Unicode addresses. NFC, then lowercase of the domain and the local part (the Greek final sigma folded to the plain one in the local part, so case variants of a Greek address stay one account; a domain keeps a typed final sigma, as IDNA2008 does). Refuses invisible, bidi, control, unassigned and compatibility characters, punycode labels, any part that mixes scripts (the Chinese, Japanese and Korean mixes with Latin are allowed), the dotless i, the IPA Extensions block (U+0250 to U+02AF) and a combining dot above on i or j. So a letter from another script, an invisible character, a compatibility form or one of those Latin letters cannot make a lookalike account. There is no UTS 39 confusables check: an address written wholly in another script, or with another same-script lookalike, is accepted as a different account, and the verification mail to that mailbox is the backstop.
  - A function `(email) => string | null`: your own policy. It must be pure, deterministic and idempotent, and return a single plain address (exactly one `@`, non-empty parts, no whitespace, commas, angle brackets or control characters, at most 254 bytes). `createAuth` runs it over a sample at startup and refuses one that throws, returns something unusable, answers differently twice, is not idempotent or merges different mailboxes; on each call an address whose result is unusable or not a fixed point is refused and logged with the error's class name only.
  
  One resolved normaliser now serves every flow (register, login, password reset, email verification, email change, invitations), every stored address and every counter key. It is exposed as `auth.normalizeEmail(email)` for your own code and as `normalizeEmail` and `parseEmail` on the plugin context; the exported `normalizeEmail` stays the `standard` policy. An unknown policy name fails at startup.
  
  Lookups by address are now exact on the core's side for every policy: a user row whose stored email is not exactly the normalised address asked for counts as not found, so a store behind a case- or accent-insensitive collation cannot reach one account under several spellings with separate lockout and rate-limit keys. `userStoreConformance` gains the case "different spellings must not match", and the plugin context gains `findCredentialByEmail`. A binary or accent-sensitive collation on the email column is recommended (see the auth-prisma README).
  
  Changing the policy on a live database needs a data migration first: rows stored under the old policy no longer match. The package does not migrate data; see the configuration reference.
  
  Upgrade note: because lookups are now exact, a row whose email was written outside the flows (an import, an admin tool, a seed) in a spelling the normaliser would not produce is unreachable, even under the default policy: its owner can no longer sign in, reset or be found by address. Before upgrading, find the rows where the stored email differs from `auth.normalizeEmail(email)` (for the default policy, any row with uppercase letters, surrounding whitespace or a non-ASCII character), then rewrite them or merge duplicates.

- [#63](https://github.com/noctcore/auth/pull/63) [`76717de`](https://github.com/noctcore/auth/commit/76717de578fbd4f83973dcf544acafeb1d5c9dad) Thanks [@Shironex](https://github.com/Shironex)! - Add email change with a revert link: `requestEmailChange`, `confirmEmailChangeCode`, `confirmEmailChangeLink` and `revertEmailChange`.
  
  - A request needs a live session with a credential proof inside `session.freshAuthAge`, then runs the new `beforeEmailChange` hooks. The two-factor plugin uses that hook: with a confirmed factor, the request needs a step-up held by the session or a code in `secondFactor`.
  - An 8-digit code (or, with `emailChange.kind: 'link'` and `urls.confirmEmailChange`, a link) goes to the new address. A taken address, or one held for another account, gets the same answer after the same store calls, and its owner gets an `email-change-in-use` mail instead. A confirm needs a live session of the same account. A pending change dies on a password change or reset and on signing out of other devices or everywhere.
  - A confirmed change voids reset and verification tokens and writes the revert link before it moves the address in one compare-and-set, marks it verified, revokes every session (re-issuing the caller's with the new re-issue via `email-changed`), and mails the old address `email-changed` with a revert link valid for `emailChange.revertTtl` (7 days, the minimum). While that link lives, the old address is held for the account: sign-up on it answers as for a taken address, and so do other accounts' changes to it.
  - A revert restores the old address and removes the password in one write, revokes every session, voids reset, verification and change tokens, keeps second factors (an owner who cannot pass one an intruder enrolled needs support), blocks the lost address for this account for `emailChange.blockAfterRevert` (30 days), and writes `email.change_reverted` with `review: true`. If the old address has an account anyway, it removes the password and sessions, answers `email_in_use`, and locks the account out: no session is issued for it, reset requests send nothing and reset links are refused, until the owner's link (kept alive as long) finishes or support calls the new `auth.clearEmailRevertLockout`, which also voids the revert link and the hold; it never lapses on its own. A revert link refuses once the account no longer names the address the change moved it to. New `auth.isAddressHeld(email)` for an app's own user-creating paths. No new change starts while a revert link lives, and password changes and resets do not void it.
  - New optional `UserStore.changeEmail`, returning `'changed' | 'taken' | 'stale'`, with conformance cases in `userStoreConformance` and an implementation in `MemoryUserStore` and `PrismaUserStore`. The flows need it and `urls.revertEmailChange`, and throw `AuthConfigError` without them. No schema change.
  - New mail events `email-change-confirm`, `email-change-in-use`, `email-changed` and `email-change-reverted`, and new `email.change_*` audit event types. A mailer or audit sink that switches over every type with a `never` check needs cases for them.
  - New doors `email-change-request`, `email-change-address`, `email-change` and `email-change-revert`; new revocation reasons `email-changed` and `email-reverted`; `OneTimeTokens.findLive`, `putKeyed`, `findKeyed` and `extendLink`; the `email.revert_lockout_cleared` audit event type.
  - `resetPassword` now checks the new password against the policy, then runs `beforePasswordReset`, and only then hashes, so a hook's refusal costs no hash. `AuthCore.checkNewPassword` and `hashCheckedPassword` split `hashNewPassword` for flows that run hooks between the two.

### Patch Changes

- [#65](https://github.com/noctcore/auth/pull/65) [`e73f7a0`](https://github.com/noctcore/auth/commit/e73f7a0096808eb2fa9f705fe6c32983fb752e08) Thanks [@Shironex](https://github.com/Shironex)! - Sign-up no longer waits on the work that differs between a taken and a new address. The answer waits on the door limit, the password hash and one insert; after that, a taken address's owner lookup, `account-exists` mail and `register.existing` audit event, and a new address's `register.created` audit event, verification token and `verify-email` mail, run in the background. On Postgres and Redis the taken path used to answer a few milliseconds slower, enough for `bun run bench:timing:stores` to tell the paths apart.
  
  On PostgreSQL and CockroachDB, the Prisma user store inserts through `createManyAndReturn` with `skipDuplicates`, so a taken address is a skipped insert instead of a failed statement. On PostgreSQL through `@prisma/adapter-pg`, a failed statement made the next query about 3 ms slower. Everywhere else the store keeps the old insert, where a unique violation answers `null`: on delegates without `createManyAndReturn` (MySQL, SQL Server), and where Prisma refuses the bulk insert with a validation error (SQLite, which has no `skipDuplicates`, and a `createData` or `select` with nested writes or relations). The store falls back on the first refusal and remembers it, so no existing setup breaks.
  
  Behaviour change: `auth.register` resolves before the verification mail is handed to the mailer and before the sign-up audit event is written. A test that reads the mail or the audit trail right after sign-up has to wait for them. A token store that fails while sign-up writes the verification code, or a user store that fails on the owner lookup, no longer fails the request. The error is logged as `Background task failed: verification mail` or `Background task failed: existing address notice`, and the user can ask for another verification mail.
